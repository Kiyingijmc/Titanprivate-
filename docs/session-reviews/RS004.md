## Does it work? (trace)

**Hash chain (§1.1/§1.3).** `compute_row_hash` (`tradebot/core/event_log.py:137-156`) hashes
`prev_hash ‖ seq ‖ schema ‖ schema_version ‖ ts_event ‖ canonical_json(payload)` exactly as
pass3-systems.md:30 specifies (field-separated by `\x1f` to avoid concatenation ambiguity — a
strengthening, not a deviation, since both write and verify paths use the same function).
`_append_locked` (`:414-506`) takes `BEGIN IMMEDIATE` up front, re-derives `head` from the last
retained row (falling back to the writer's own `log_meta` marker if rows are missing — the
mechanism that makes a lost tail detectable at `:446-453`), and commits the row + updated
`chain_head_seq`/`chain_head_hash` meta atomically. `verify_chain` (`:534-618`) walks gaplessness,
genesis `prev_hash`, per-row `prev_hash` continuity, payload decodability, `row_hash`
recomputation, sidecar hashes, and tail-vs-marker agreement, in that order, raising
`RecoveryRequired` (never returning a partial/soft result) on any break. This is a faithful,
careful implementation of §1.3's `verify_and_replay` chain-walk half.

**The five corruption drills** (`tests/unit/test_tradebot_event_log.py:218-322`,
`TestCorruptionDrills`) are the M0 acceptance bar cited in both the backlog
(`_BACKLOG.md:16`) and `pass8-synthesis.md:225`: truncate (`test_drill_1_*`, `:230-247`,
including a second case proving a truncated log also refuses further appends, not just
`verify_chain`), payload bit-flip (`test_drill_2_*`, `:249-260`), `row_hash` bit-flip
(`test_drill_3_*`, `:262-270`), deleted middle/first row (`test_drill_4_*`, `:272-286`), and
corrupt snapshot sidecar in all three of its failure shapes — tampered-but-valid-gzip,
damaged-gzip-stream, and missing file (`test_drill_5_*`, `:288-315`). I hand-traced each against
`verify_chain`/`_verify_sidecar` and every one lands on the intended `RecoveryRequired` branch
with the asserted message substring; none of the five can produce a clean boot. This is the
session's headline deliverable and it is solid.

**Determinism** (`TestDeterminism`, `:187-215`) proves identical event streams (different
`ts_ingest` clocks on purpose) produce byte-identical chain heads, and a differing payload
diverges the head — matching pass8 M0 acceptance (b).

**Snapshots, archive, backup** are all implemented per §1.3's cadence (10k events / 24h,
whichever first), sidecar-spill-over-256KB, second-newest-snapshot archive boundary, and
`VACUUM INTO` + gzip + restore-verify backup job. Two problems surfaced in this part of the
trace, detailed below.

## Findings

### CRITICAL — `backup_and_verify` never captures the snapshot sidecar directory, and `verify_backup` masks this by checking the *live* local directory instead of anything the archive actually contains

`tradebot/core/event_log.py:812-843` (`backup_and_verify`) does exactly one thing to the
filesystem: `VACUUM INTO` the SQLite file, then gzip it. It never touches
`self._snapshot_dir` (`snapshots/*.json.gz`, written at `:686-696`) — the directory holding any
snapshot payload larger than `snapshot_inline_limit` (default 256 KB). `verify_backup`
(`:845-908`) then restores that lone `.sqlite3.gz` to a temp path and opens a probe `EventLog`
against it with `snapshot_dir=self._snapshot_dir` (`:869`) — **the same, live, original
directory**, not anything extracted from the archive. `_verify_sidecar` (`:620-635`) resolves
`self._snapshot_dir / Path(sidecar_path).name`, so of course the file is found: it was never
moved, copied, or otherwise part of the "backup" at all.

Per pass3-systems.md §1.3, the entire point of this job is: *"Nightly ... `VACUUM INTO` a dated
copy → zstd → **off-box**... The job then restores the backup to a temp path and runs the full
chain walk + a projection smoke-build; a backup that fails verification raises CRITICAL. An
unverified backup is treated as no backup."* A backup artifact that is actually shipped off-box
(the stated purpose) would arrive without `snapshots/`, and any snapshot event whose payload
spilled to a sidecar would be permanently unreconstructable from it — yet this code returns
`{"verified": True, ...}` for exactly that artifact, because the check silently substitutes the
still-present local directory for whatever the archive should have contained.

**Failure scenario:** the nightly job runs, `backup_and_verify` reports `verified: True`, ops
ships `events-<ts>.sqlite3.gz` off-box per the design's own instruction. The primary host is
lost (disk failure, the actual disaster this job exists for). Restore from the off-box copy: any
`snapshot.projection` row citing a sidecar (`payload["sidecar"]`) now fails `_verify_sidecar`
with "snapshot sidecar missing" — the exact `RECOVERY_REQUIRED` this job was supposed to have
already ruled out. The false-positive `verified: True` is arguably worse than no verification at
all, since it is the only tested basis so far ("an unverified backup is treated as no backup")
for trusting the backup was survivable.

This is not a documented, deliberate scope cut: the module's own "Scope notes" preamble
(`:21-31`) discloses three other narrowings (gzip vs zstd, `dest_dir` being local rather than
off-box, projection content arriving in M0-4) but says nothing about sidecars being excluded from
the backup body. `test_backup_of_a_log_whose_sidecar_is_corrupt_fails_loudly`
(`tests/unit/test_tradebot_event_log.py:537-545`) inadvertently demonstrates the gap: it proves
`verify_backup` fails when the *live* sidecar is corrupted after the backup was taken — which
only works because the check depends on the live directory, not on anything the backup itself
carries.

**Suggested fix (for whoever remediates):** `backup_and_verify` should copy (or otherwise bundle,
e.g. into the same dated archive or a sibling one) `self._snapshot_dir` into `dest_dir` alongside
the SQLite dump, and `verify_backup` should restore sidecars from *that* copy — not accept an
externally-supplied `snapshot_dir` that defaults to the live original.

### MAJOR — `archive_before` is not crash-safe: a failure between the Parquet write and the DB delete/commit duplicates rows in the archive on retry

`tradebot/core/event_log.py:742-808`. The method (a) writes one or more month-bucketed Parquet
files via `_write_parquet` (`:782-787`), then (b) opens a *separate* `BEGIN IMMEDIATE` transaction
to `DELETE FROM events WHERE seq<?` and bump `archived_through_seq` (`:789-800`). These two steps
are not atomic with each other. `_write_parquet` (`:944-994`) is a read-modify-write: if the
target month file already exists, it reads it back and **concatenates** the new rows onto it
(`:976-979`) with no de-duplication by `seq` (Parquet has no unique-constraint mechanism, and none
is applied at the `pyarrow.Table` level either).

**Failure scenario:** the nightly archive job calls `archive_before(8)`; step (a) successfully
writes `events-202603.parquet` for seq 1-7; the process is killed (OOM, host reboot, `kill -9` —
exactly the chaos-tier scenario pass3 §7.4 names as a first-class CI concern for this milestone)
before step (b)'s transaction commits. SQLite still holds seq 1-7 (nothing was deleted, chain
still verifies). The next run of the job — automatic retry or the following night — calls
`archive_before(8)` again with the same eligible boundary; `_write_parquet` reads back the
already-written `events-202603.parquet` (which contains seq 1-7) and appends seq 1-7 *again*,
producing a Parquet file with every archived row duplicated. `archived_through_seq` and the live
SQLite chain remain correct throughout — the corruption is confined to the archived audit trail,
but that is precisely the artifact this milestone exists to make trustworthy (`D-007`: "chained
event log + snapshots + archive + backup/restore-verify"). No test in `TestArchive`
(`tests/unit/test_tradebot_event_log.py:396-484`) exercises a retry after a partial failure, so
this is latent rather than demonstrated by the suite, and it sits outside the five named
corruption drills — but it is new code this session wrote, in the money-truth path, with a
plausible crash window.

**Suggested fix:** either make `_write_parquet` idempotent under retry (write to a temp file and
atomically rename, and/or dedup on `seq` before writing), or reorder so the DB delete/commit
happens *before* any Parquet write is considered durable (e.g. write-ahead a manifest of what was
archived, or make the whole operation retry-safe by checking `archived_through_seq` against what
the target Parquet file's own `chain_last_seq` metadata already claims before re-writing).

## Three-axis readiness

- **Does it work:** mostly. The headline deliverable — the hash chain and all five corruption
  drills — is correct and well-tested by trace. The backup and archive lifecycle, also claimed by
  this session's scope (§1.3's "snapshots every 10k/24h, archive, backup + restore-verify job" in
  the backlog line), has one false-positive verification bug (CRITICAL) and one crash-retry
  duplication bug (MAJOR), neither caught by the committed suite.
- **Is it safe:** additive-only, confined to `tradebot/`, no existing Titan v14 code touched, no
  new unvetted dependency (pyarrow was already present). Safe to have on a branch; not yet safe to
  treat the backup job's `verified: True` as a real disaster-recovery guarantee.
- **Is it worth it:** yes — the chain/drill work this session was actually scoped and graded
  against (the backlog's own acceptance line) is done well. The two findings are real but scoped
  and fixable without touching anything outside this session's own file.

## Verdict

The five corruption drills — this session's explicit acceptance bar — are implemented correctly
and traced clean. But the same session also shipped the backup and archive halves of §1.3, and
both have real integrity gaps: a backup verification that can't actually detect the one failure
mode it exists to catch (sidecar loss on a genuinely off-box restore), and an archive path that
duplicates data on a plausible crash-retry. For a component explicitly flagged RISKY-ADJACENT as
"the money-truth substrate," both need a remediation pass before this is trusted as the F-004
foundation the next two sessions (`m0-4`, `m0-5`) will build on.
