## CRITICAL — a resting LIMIT's risk leaves the aggregate within ~60 s, so the cap still does not bind across bars

`aggregate_open_risk` reads resting orders from
`state_manager.get_pending_orders()` (`src/core/system_controller.py:414-416`),
which returns `active_orders` rows with `status='PENDING'`
(`src/core/state_manager.py:240-244`). That table is swept every 60 s by the
Sync Guard, which S013 did not touch:

- `_perform_reconciliation` builds `mt5_tickets` from `current_open_positions`
  **only** (`src/core/system_controller.py:374`);
- `reconcile_state` selects **every** row in `active_orders` — no status filter
  — and returns any ticket not in that list (`src/core/state_manager.py:169-182`);
- `archive_trade` then `DELETE`s it (`src/core/state_manager.py:196`);
- and a resting LIMIT is never in `current_open_positions`: the EA builds `pos`
  from `PositionsTotal()` and reports pending orders on the separate `orders`
  key (`mql5_bridge/Experts/Titan_Gateway.mq5:180, 209`).

So every PENDING row is deleted on the first reconciliation tick after it is
registered (`self.recon_interval = 60`, `src/core/system_controller.py:178`,
fired at `:313-315`). Verified against the real `StateManager`:

```
pending after register:  [(111, 'PENDING')]
ghosts reported:         [111]
pending after ONE sweep: []
```

The in-flight reservation does not cover the gap: it is released as soon as the
heartbeat sees the DB row (`_release_reserved_risk`,
`src/core/system_controller.py:489-504`) and in any case expires at
`RESERVED_RISK_TTL_S = 300`. A SilverBullet limit lives 12 bars — **12 hours** on
H1 (`src/core/system_controller.py:785-791`). Between roughly one minute and
twelve hours after placement, its risk is invisible to the cap.

Repro, modelling the real controller ordering (bar close → N × `_execute_signal`
with no bridge drain between them → `EXECUTION:OPENED` registers each PENDING row
→ HEARTBEAT → 60 s Sync Guard), 6 pairs, 1 % sizing, shipped 5 % cap,
$10,000 equity, real `StateManager`:

```
H1 #1 -> dispatched 5 of 6                      <- cap works WITHIN a bar
   DB pendings: 5 | reserved $: 0.0 | aggregate: 495.00
   after Sync Guard -> DB pendings: 0 | reserved $: 0.0 | aggregate: 0.0
H1 #2 -> dispatched 5 of 6
H1 #3 -> dispatched 5 of 6

limits resting after 3 bars: 15 | lots 14.85 | true risk $1485 = 14.8% of equity
                                                          vs a 5.00% cap
```

Fifteen resting limits carrying 14.8 % of equity against a 5 % ceiling, and the
gate logs zero blocks after the first bar. The in-cycle protection added this
pass is real and works; what it protects is a snapshot that resets to zero every
minute.

This is not a defect the session introduced — `reconcile_state`'s missing status
filter is pre-existing on `main` and unchanged by this diff. It is reported here
because it is the reason the session's own headline remediation does not bind in
production, which is the session's Definition of Done. Two corroborating symptoms
confirm the reading rather than contradict it: the 12-bar TTL cancel in
`_cleanup_ghost_orders` (`src/core/system_controller.py:718-728`) can never fire,
because the rows it iterates are deleted long before their TTL; and the operator
receives a spurious `⚠️ Sync Guard: Resolved Ticket #N (Closed externally)`
Telegram for every limit Titan places (`:377`).

It also makes the sentence this session added to `CLAUDE.md:40` — "it sums
risk-to-stop over open positions, resting pending orders and in-flight sends" —
untrue of the running system.

**Remediation (either shape works, the first is smaller):**
- exclude PENDING rows from the ghost sweep — `reconcile_state` should consider
  only rows the heartbeat's `pos` list can actually corroborate — which also
  revives `_cleanup_ghost_orders` and stops the false "Closed externally"
  notifications; or
- source the resting set from something the sweep does not clear.

Either way the remediation needs a test at the seam that the current
`FakeStateManager` cannot express: it hands back a fixed `pending` list forever
(`tests/unit/test_risk_manager_exposure_cap.py:228-244`), so
`RestingPendingOrderTests` passes against a book state production never reaches.
Drive one case through a real `StateManager` and a `_perform_reconciliation`
call, or the same green-suite-next-to-a-dead-cap situation repeats.

## MINOR — reservations are released per symbol, not per order

`_release_reserved_risk` drops a symbol's entire reservation as soon as *any*
row for that symbol is visible (`src/core/system_controller.py:499-504`).
`check_exposure` blocks a duplicate only against open **positions**
(`src/risk/exposure.py:97-101`), so a second limit on a symbol that already has
one resting is permitted; at the next heartbeat the older DB row makes the
symbol visible and the newer order's reservation is discarded before its own
`EXECUTION:OPENED` has landed. The window is one drain cycle and the CRITICAL
above currently masks it, but once the pending source is durable this becomes
the remaining under-count. Keying reservations by ticket (or releasing them in
the `OPENED` handler, where the ticket is known) closes it.

## MINOR — two silent gaps in an otherwise strict fail-closed contract

Both leave the aggregate *understated*, which is the direction the rest of this
component refuses to guess in:

- **Manually placed pending orders are invisible.** An operator limit placed in
  MT5 has no DB row, and the heartbeat's `orders` rows carry no `sl`
  (`mql5_bridge/Experts/Titan_Gateway.mq5:225`) so they cannot be priced. Note
  the asymmetry: a manual stopless *position* halts every symbol
  (`src/risk/risk_manager.py:277`, `:331`), while a manual *pending order* is
  silently ignored. Not necessarily fixable without an EA change (out of scope),
  but the docstring and `CLAUDE.md:40` currently imply coverage that does not
  exist.
- **`lots == 0.0` reads as un-computable** (`src/risk/risk_manager.py:277`),
  and the `active_orders.lots` column defaults to `0.0`
  (`src/core/state_manager.py:103`). Every PENDING row S013 will see is written
  from `pending_signal_meta` and does carry lots, so this is latent — but a row
  surviving from a pre-`lots` schema would take the whole book un-computable and
  halt all 11 pairs. Today the Sync Guard deletes it within 60 s; after the
  CRITICAL is fixed it would persist. Worth a defensive skip-or-alert rather
  than a permanent silent halt.

## Three-axis readiness

- **Does it work?** Within a single bar sweep, yes — I reproduced the 6th signal
  of a sweep being correctly blocked at 4.95 %. Across bars, no: the resting-limit
  aggregate returns to `0.0` within ~60 seconds of an order being placed, and I
  reproduced 14.8 % of equity resting against a 5 % cap with no blocks logged
  after the first bar.
- **Is it safe?** The fail-closed discipline and the operator alert are right,
  and the commission basis is now exact. The residual risk is the same one the
  session exists to remove: sustained portfolio exposure well past the configured
  ceiling under the live LIMIT-only configuration, on an account currently
  forward-testing unattended.
- **Is it maintainable?** Yes, and notably so. Docstrings explain *why* rather
  than *what*, the idioms match the surrounding code, the throttle/TTL constants
  are named class attributes, and the test file's module docstring records the
  reasoning. The remaining fix is small.

## Verdict rationale

The remediation pass answered every round-1 finding honestly and the in-cycle
reservation work is genuinely good. But the pending-order source it chose is
cleared by an unmodified 60-second sweep, so the delivered control still cannot
block a trade beyond the bar in which the first order was sent. Recording
"cross-symbol exposure cap: DONE" against that would be the second consecutive
green suite sitting next to a non-binding cap — precisely what this chain's
standing lesson warns about. One more pass, with a seam test that uses a real
`StateManager`, closes it.
