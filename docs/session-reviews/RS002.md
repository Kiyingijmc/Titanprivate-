## What the task required

deterministically in a worktree without an ambient `data/specs.json`** (i.e. when

## Finding

**CRITICAL — the fixture reproduces the failing spec, not the passing one; the flake is not fixed.**

`tests/unit/test_research_run.py:196-199` (the new code) pins the fixture to:
```python
{"BTCUSD": {"tick_size": 1e-5, "tick_value": 1.0, "vol_step": 0.01}}
```
This is **byte-for-byte identical** to `_DEFAULT_SPEC` in `scripts/research_run.py:61`
(`{"tick_size": 1e-5, "tick_value": 1.0, "vol_step": 0.01}`) — the exact fallback spec the
diagnosis identifies as the **failing** branch, not the passing one. Passing `--specs
<fixture>` with this content is functionally indistinguishable from what the test already did
before this session's change, in any worktree lacking an ambient `data/specs.json` (which this
review worktree confirms is the case — `data/specs.json` does not exist here, and it's
gitignored per `.gitignore:21`). The nondeterminism is removed, but the value it's pinned to is
the one the diagnosis says fails.

Tracing why it fails, via `tests/backtest/backtest_engine.py:148-170` (`trade_dollars`) and
`scripts/research_run.py:277-284` (`_signals_to_trades`):

- `test_data.csv:2` shows BTCUSD trading around **$91,000**. Any real SL distance for an H1
  `silver_bullet` signal on this instrument is on the order of tens to hundreds of dollars.
- With `tick_size=1e-5` (a 5-digit-forex constant, not a crypto-appropriate one),
  `stop_ticks = abs(entry - sl) / 1e-5` — for even a $1 stop this is already `100,000`.
  `money_per_lot = stop_ticks * tick_value(1.0)` is therefore always ≥ `100,000` for any
  realistic signal.
- `lots = floor((1000 / money_per_lot) / 0.01) * 0.01` (risk_dollars=1000,
  `DEFAULT_RISK_DOLLARS` at `scripts/research_run.py:60`, `vol_step=0.01`). Solving for the
  break-even point: lots first becomes non-zero only when `money_per_lot ≤ 100,000`, i.e. an SL
  distance **≤ $1** on a $91,000 instrument (≈0.001%). No real signal in this dataset has a
  stop that tight, so **`lots == 0.0` for every trade**.
- `trade_dollars` then returns `commission = lots * commission_per_lot = 0` and
  `spread_cost = spread_points * tick_value * lots = 0` regardless of `spread_points` (5 vs
  500 in the two test legs) — `net = gross - 0 - 0 = gross`.
- `net_r = dollars["net"] / DEFAULT_RISK_DOLLARS` (`scripts/research_run.py:283`) therefore
  equals the raw gross `r` for every trade, **identically for both the cheap and expensive
  spread runs** — spread has been rendered mathematically invisible.
- `aggregate_metrics` (`tests/backtest/backtest_engine.py:115`) computes `expectancy =
  total_r / n` over these now-identical `r` values, so `cheap_card["metrics"]["is"]
  ["expectancy"]` and `expensive_card[...]["expectancy"]` will be **exactly equal**.

The test's own assertion at `tests/unit/test_research_run.py:221-224`
(`self.assertNotEqual(cheap_expectancy, expensive_expectancy)`) will therefore raise, and the
test fails — not flakily, but **deterministically**, exactly reproducing the failure mode the
diagnosis already identified for the "no ambient specs.json" branch. This session has converted
an intermittent failure (workspace-dependent) into a fixed, always-reproducible one, which is a
regression against the DoD's implicit bar ("VERIFY_CMD passes clean, zero regressions") and
against the task's actual purpose (make this test reliably **pass**).

The correct fix is the same shape (pin an explicit `--specs` fixture so the test doesn't depend
on ambient files) but with a **crypto-appropriate tick_size** (e.g. matching order-of-magnitude
what a real FBS `data/specs.json` entry for BTCUSD would contain — on the order of `0.01`, not
`1e-5`) so that lot sizing is non-degenerate and spread cost actually flows into `net_r`, per the
"passed... WITH it" branch of the diagnosis.

**Failure scenario:** running `.venv/bin/python -m unittest tests.unit.test_research_run
-v` on this branch, in any environment without a pre-existing `data/specs.json` (which is now
gitignored, so this is the common case going forward) — the exact scenario `VERIFY_CMD` runs in
a fresh worktree — should show `TestSpreadFlowsIntoNetR.test_different_spreads_produce_different_expectancy`
FAIL with `AssertionError` on the `assertNotEqual` at line 221, both expectancy values equal.

## Other observations (non-blocking)

- The backlog's diagnosis also names a **"tearDown reset"** as part of the prescribed fix
  (presumed necessary for a suspected global spec-state leak). Tracing `research_run.py` and
  `backtest_engine.py`, there is no module-level mutable cache of specs — `_load_specs` reads
  the given path fresh every call, and `trade_dollars`/`_signals_to_trades` take `spec` as a
  plain argument. A `tearDown` reset genuinely isn't needed once the test is hermetic; dropping
  it is a sound simplification, not a shortcut around the real root cause. Flagged only for
  completeness, not as a defect.
- Commit message (`chore(S002): snapshot build output for review`) is generic boilerplate and
  doesn't describe the actual change (pin `--specs` to a fixture). Cosmetic only — not scored as
  a finding.

## Verdict

The session correctly diagnosed *where* the flake test needed to change and made a minimal,
correctly-scoped, hermetic-fixture-shaped edit — but pinned the fixture to the spec values the
project's own diagnosis had already identified as the **failing** branch, not the passing one.
The result is very likely a test that now fails every time `VERIFY_CMD` runs in a clean
worktree (the normal case, since `data/specs.json` is gitignored), rather than the intermittent
flake it was supposed to resolve. This is a correctness defect in the delivered fix, not a
question of taste or scope.
