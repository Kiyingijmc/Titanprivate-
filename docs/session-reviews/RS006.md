## Does it work?

**Schema-keyed dispatch (adapted, not rebuilt).** `tradebot/core/bus.py:76-99`'s
`publish` keys on `envelope.schema` (a string) instead of `type(event)` — the correct
adaptation, since every `tradebot` event is a single `Envelope` class differentiated by
its `.schema` field, unlike `src/core/bus.py`'s per-event-type Python classes. In-order,
synchronous, deterministic delivery within one `publish` call is preserved verbatim
(`TestSchemaKeyedDispatch.test_typed_delivery_in_order`,
`tests/unit/test_tradebot_bus.py:26-33`, asserts subscriber-registration-order
delivery). `subscribe_all` (`bus.py:73-74`) and per-subscriber `stats()`
(`bus.py:101-107`, now carrying a `tier` key) both carry over from the source module.

**Normal-tier circuit breaking is byte-behavior-identical to `src/core/bus.py`.**
`bus.py:93-98` reproduces `src/core/bus.py:69-77`'s consecutive-failure counter and
circuit-open-after-`max_failures` logic exactly, and `publish` never raises for a
normal-tier subscriber's exception (`test_throwing_subscriber_is_isolated_and_
circuit_broken`, `:53-67`, five publishes against a subscriber that always throws with
`max_failures=3`: the good subscriber runs all 5 times, `bad` shows `failed=3` — capped
by circuit-open, not 5 — and `circuit_open=True`). `test_success_resets_failure_count`
(`:69-81`) confirms a success resets `consecutive` to zero, mirroring
`src/core/bus.py:66`.

**Critical tier is the actual new behavior this session was scoped to add, and it
matches the spec line precisely.** `bus.py:86-92`: on a critical-tier subscriber's
exception, the bus logs at `CRITICAL` and re-raises out of `publish` — never sets
`circuit_open`, never increments `consecutive` (both dead code paths for that tier, by
construction — the `raise` exits before either line executes). This is exactly pass3's
"§6.1 ADD ... critical subscribers ... are never circuit-broken — their exception
halts-and-alerts instead of being swallowed." Three tests exercise this directly:
`test_critical_exception_is_reraised_and_halts_remaining_subscribers`
(`:85-97`) proves both the re-raise *and* that a subscriber registered after the critical
one never runs (a real "halts remaining delivery for this publish call" assertion, not
just "an exception happened somewhere"); `test_critical_tier_never_circuit_breaks`
(`:99-114`) runs `max_failures=1` for 5 publishes and confirms `circuit_open` stays
`False` and `failed` reaches 5 — the counter that would trip circuit-breaking for a
normal-tier subscriber under the same failure count never does so here;
`test_unknown_tier_rejected` (`:117-121`) confirms `subscribe(..., tier="urgent")`
raises `ValueError` (`bus.py:68-69`) rather than silently defaulting.

**STA skeleton matches the "generic, schema-agnostic mechanism" framing the backlog
explicitly scoped this to.** `tradebot/core/sta.py:48-100`'s `SignalTransitionActor` is
a single `asyncio.Queue` drained by exactly one `_consume` task
(`_ensure_consumer`/`_consume`, `:56-58,75-87`), so at most one `(guard, apply)` request
is ever mid-processing — the pass3 §2.1 "one asyncio task ... processes one request at a
time" property. `TestFifoOrderingAndSingleConsumer.test_single_consumer_serializes_and_
preserves_fifo_order` (`tests/unit/test_tradebot_sta.py:26-65`) is a real concurrency
test, not a trivial sequential one: it submits three requests, blocks the first mid-`apply`
on an `asyncio.Event`, confirms via `await asyncio.sleep(0)` that requests 1 and 2 are
still untouched while 0 is blocked (proving true serialization, not just eventual FIFO
output order), then releases and confirms final order `[0, 1, 2]`. Guard evaluation
happens inside the consumer at processing time (`_process`, `:89-100`), matching "guards
are evaluated *inside* the handler" (pass3-systems.md:146) — a failed guard resolves to
`TransitionOutcome(accepted=False, reason="race_loser")` without calling `apply()` at all
(`test_guard_fail_resolves_to_race_loser_without_raising_and_apply_never_runs`,
`:69-84`, uses an `apply` that raises `AssertionError` if ever invoked — a real "this
must not run" assertion, not just an unasserted mock). A passed guard's `apply()` result
is published through the injected `EventBus`
(`test_guard_pass_publishes_through_injected_bus_and_subscriber_observes_it`, `:86-101`,
confirms both that the subscriber actually received the envelope *and* that
`outcome.envelope is received[0]` — the same object, not a copy).

## Findings

None rise to CRITICAL or MAJOR. Two MINOR, forward-looking gaps — in the same spirit as
the MINORs `RS003` raised against the M0-2 skeleton (robustness gaps aimed at code that
doesn't exist yet, not defects in what's here):

### MINOR — `SignalTransitionActor.aclose()` silently abandons any request still queued (never processed), leaving its caller's `submit()` awaiting a future that will never resolve

`tradebot/core/sta.py:66-73`: `aclose()` cancels `self._consumer` and awaits its
cancellation, but does nothing with `self._queue`'s remaining contents. If `submit()` A
is queued but not yet dequeued when `aclose()` is called (e.g. a caller triggers shutdown
while a burst of transitions is still in flight), `_consume`'s `while True` loop is
cancelled before it ever calls `self._queue.get()` for A's request, so A's `future` is
never resolved — the coroutine `await`ing `actor.submit(...)` for A hangs forever (not
merely errors; genuinely never completes) unless the caller wraps it in an external
timeout. No test exercises `aclose()` with items still queued — both `test_tradebot_sta.py`
scenarios always `await asyncio.gather(...)` every submitted request before calling
`aclose()`. This is inert today (nothing outside the test suite calls `SignalTransitionActor`
yet — it is explicitly a skeleton per the module docstring, `sta.py:1-19`), but is worth
tracking before M1 wires real signal-lifecycle callers onto this actor, since a
hang-on-shutdown bug is easy to miss until it strands a real coroutine in production.

### MINOR — no test exercises a critical-tier bus exception propagating through the STA's `_process`/`submit` path

`sta.py:96-99` calls `self._bus.publish(envelope)` synchronously inside `_process`; if
that `envelope`'s schema has a critical-tier subscriber that raises, the exception
propagates out of `_process`, is caught by `_consume`'s `except Exception as exc` (`:80-82`),
and is correctly set on the request's future (so `await actor.submit(...)` re-raises it
to the caller rather than crashing the actor's consumer loop) — I traced this and it
looks correct by construction, but it is untested. Both `test_tradebot_bus.py`'s
critical-tier tests and `test_tradebot_sta.py`'s guard/apply tests exercise the two
halves of this interaction independently; nothing exercises them together. Low risk
today (same "nothing calls this yet" reasoning as above) but is the one interaction
between this session's two new modules that determines whether a critical-tier failure
during a real signal transition surfaces cleanly to the caller or wedges the actor —
worth a direct test before this is load-bearing.

## Observations (not findings)

- **`events.py`'s one-line change is a legitimate, well-precedented carry-over fix, not
  scope creep** — same pattern S004→S005 established for fixing a small cross-file gap a
  prior review flagged, done here with full test coverage and an explicit RS003
  citation in the new test's comment (`test_tradebot_events.py:116-120`).
- **The async fire-and-forget path from `src/core/bus.py` was deliberately dropped**,
  documented at `bus.py:20-21` ("nothing under `tradebot/` has an event loop yet") — a
  correct, disclosed simplification rather than a silent capability loss; the STA (not
  the bus) is where `tradebot`'s asyncio integration lives for now.
- **Test file placement is flat under `tests/unit/`**, consistent with the S003–S005
  precedent and its stated reason (a `tests/unit/tradebot/` package would shadow the real
  `tradebot` package under `unittest discover -s tests/unit`).
- `bus.py:78` rebuilds `self._by_schema.get(envelope.schema, []) + self._all` as a new
  list on every `publish` call — a minor allocation, not a correctness issue, and
  identical in shape to `src/core/bus.py:52`'s existing pattern.

## Three-axis readiness

- **Does it work:** yes, on the backlog's own acceptance line (ADAPT `src/core/bus.py`'s
  deterministic delivery + stats, ADD a critical tier that halts-and-alerts instead of
  being swallowed, plus an STA skeleton that serializes one request at a time with
  processing-time guard evaluation). Hand-traced clean against both the source module it
  adapts and the pass3 spec text; unrun `VERIFY_CMD` is a disclosed open item, not a
  finding.
- **Is it safe:** yes. Additive except for one precedented, fully-tested one-line fix to
  an existing dataclass field; zero new dependencies; nothing under `src/` (the live v14
  ZMQ system) touched or reachable from this code; nothing in `tradebot/` is wired into
  anything that runs today, so the two MINOR gaps above have no live blast radius yet.
- **Is it worth it:** yes. This is the concurrency substrate the M1 signal lifecycle
  (§2.1) will serialize through, landed with the scope discipline the backlog asked for
  (ADAPT, not rebuild, the bus; skeleton, not implementation, for the STA) and tests that
  actually exercise concurrency semantics (blocked-mid-processing FIFO ordering, guard-
  never-calls-apply-on-reject) rather than just happy-path sequencing.

## Verdict

Clean, scope-disciplined work that delivers exactly the backlog's ADAPT-bus +
STA-skeleton scope, with one legitimate carry-over fix and real concurrency-aware tests.
The two MINOR findings are both forward-looking robustness gaps in code nothing calls
yet (matching the bar RS003 set for MINOR-not-blocking on the prior skeleton session),
not defects in what this session actually claims to deliver.

MIG-VERDICT: PASS
