## What was built

A portfolio-wide $-risk ceiling:

- `RiskManager.aggregate_open_risk` (`src/risk/risk_manager.py:247-283`) sums
  `money_for_move(s, |p - sl|, vol)` over heartbeat position rows, returning
  `None` ("un-computable") if any single row is stopless or lacks broker specs.
- `ExposureManager.check_total_risk` (`src/risk/exposure.py:44-76`) blocks when
  `(open + proposed) / equity` exceeds `risk.account.max_total_open_risk_pct`.
- `SystemController._execute_signal` (`src/core/system_controller.py:387-398`)
  calls it after the existing count/correlation gate and before the order send.
- `config/config.yaml:48` ships the cap at `5.0`.

Things that are genuinely right and I want on the record: the arithmetic is
correct and asset-agnostic (it reuses the broker-spec `money_for_move` path, so
no forex-shaped assumptions leak in); the ceiling is inclusive and that boundary
is pinned by a test; the equity `<= 0` guard prevents a divide-by-zero before a
heartbeat; the `abs()` over-statement for ratcheted stops is conservative in the
safe direction and is documented; the gate sits before `send_order_reliable`, not
after; and the unit-level tests for the two new functions are thorough and
readable.

The problem is not the gate's math. It is **what the gate is allowed to see.**

## CRITICAL — the cap ignores unfilled pending orders, so it cannot bind under the shipped configuration

`_execute_signal` feeds the gate `self.current_open_positions`
(`src/core/system_controller.py:391`), which is bound only from the heartbeat's
`pos` key (`src/core/system_controller.py:578`). Pending LIMIT/STOP orders arrive
on a *separate* key and land in `current_pending_orders`
(`src/core/system_controller.py:579`; EA source `mql5_bridge/Experts/Titan_Gateway.mq5:239`).
`aggregate_open_risk` therefore contributes **zero** for every order that has been
placed but not yet filled.

That would be a corner case if Titan mostly sent market orders. It does not.
SilverBullet — per `CLAUDE.md` the *only* approved strategy — returns
`{'type': 'LIMIT'}` on both sides (`src/strategies/models/silver_bullet.py:118,128`),
across 11 pairs (`config/config.yaml:121-122`), and a placed limit lives for 12
bars of the strategy timeframe — H1, so **12 hours** — before ghost cleanup
cancels it (`src/core/system_controller.py:668-674`). So in the live config the
normal state of the book is "several limits resting, nothing filled yet", which
is exactly the state in which the new gate computes `0.0` and waves everything
through.

Reproduced against the session's own fixtures (`_controller` with an empty book,
the shipped 5% cap, decision `type` flipped to `LIMIT`, 1%-of-equity sizing):

```
orders sent through the 5% cap: 11 -> committed risk 11.0% of equity
cap blocks logged: 0
```

Eleven orders, none blocked, 11% of equity committed against a 5% ceiling — a
2.2× breach of the exact quantity this session exists to bound. Nor is it caught
later: the `EXECUTION`/`OPENED` handler
(`src/core/system_controller.py:500-526`) registers the fill and notifies, but
re-runs no risk gate, so once the limits fill the account simply carries the
excess.

The data needed to close this is already persisted — `register_order` stores
`initial_sl` and `lots` for `status='PENDING'` rows
(`src/core/state_manager.py:120-135`), and `get_pending_orders()`
(`src/core/state_manager.py:240-244`) already returns them for the TTL sweep.
(Note the heartbeat `orders` rows are *not* a usable source: EA line 225 emits
`t,s,p,type,vol` with no `sl`.)

**Remediation:** include resting pending orders in the aggregate — same
fail-safe discipline, same `money_for_move` call — sourced from
`state_manager.get_pending_orders()`.

## MAJOR — no in-cycle reservation: orders sent earlier in the same bar sweep are invisible

`current_open_positions` is rebound only when a HEARTBEAT is processed
(`src/core/system_controller.py:578`). A bar close drives
`_run_strategies` → `arb.resolve(...)` → a `for intent in approved:` loop that
awaits `_execute_signal` once per approved intent
(`src/core/system_controller.py:766-773`), and that loop never mutates the book.
Every signal in the sweep is therefore measured against the *same* snapshot, and
N trades that are each individually under the cap all pass. This is independent
of the CRITICAL above — it bites market orders too (`_execute_signal` flips a
near-touch LIMIT to MARKET at `src/core/system_controller.py:366-370`).

The repo already knows this failure mode and already solved it for the *count*
cap: `Arbiter._apply_caps` deliberately counts `open + approved_this_cycle`
(`src/arbiter/arbiter.py:256-277`, and the plan calls it out verbatim —
`docs/superpowers/plans/2026-07-13-plan-05-arbiter-v15_2.md:117`). The new $ cap
ships without the equivalent, so the money gate is strictly weaker than the count
gate sitting next to it.

**Remediation:** accumulate risk actually dispatched during the current cycle (or
have the gate read a "committed" total that a successful `send_order_reliable`
increments) so the second and later signals of a sweep see the first.

## MAJOR — one un-pricable position silently halts trading on every symbol

`aggregate_open_risk` returns `None` if **any** open row has `sl == 0` or a symbol
whose broker specs never loaded (`src/risk/risk_manager.py:276-281`), and
`check_total_risk` then blocks (`src/risk/exposure.py:66-68`). Failing closed is
the right instinct and matches house style — but note the blast radius is not the
same as the precedent it cites. `calculate_lot_size`'s fail-safe skips *the symbol
it cannot size* (`src/risk/risk_manager.py:153-160`); this one blocks *the entire
book, on every symbol, indefinitely*, on the strength of one unrelated row.

Realistic triggers, all outside the bot's control:

- the operator opens or hedges a position manually in MT5 without an SL (the
  heartbeat reports `sl` as `0.0`, `Titan_Gateway.mq5:194`);
- a restart where a "cold" symbol returns no history on the first `GET_HISTORY`
  so specs never load — behaviour `CLAUDE.md` documents explicitly — while a
  position on that symbol is open;
- a symbol dropped from strategy `pairs` while a position on it is still open, so
  it never receives specs again.

And the outage is invisible. The only signal is
`logger.log_event("RISK", "EXPOSURE", ...)` into the audit log
(`src/core/system_controller.py:396-398`). There is no Telegram notification,
unlike essentially every other operator-relevant event in `telemetry`. A
multi-day full trading stop would look exactly like a quiet market. Given a
demo-forward test is running unattended right now, that matters.

**Remediation:** keep the fail-closed semantics, but make a book-wide
un-computable state operator-visible (a throttled Telegram alert on first
occurrence is enough), and/or scope the halt narrowly enough that one stray
manual position cannot mute all 11 pairs.

## MINOR — the gate compares gross risk against a net-risk sizing contract

`calculate_lot_size` solves for risk **net of commission** (the two-step solver at
`src/risk/risk_manager.py:173-187`, `static_commission_usd: 7.0`), while
`money_for_move` is gross-only (`src/risk/risk_manager.py:232-245`). So both the
proposed trade and every open position are under-counted by `lots × $7`, and the
cap admits somewhat more true risk than configured. Small — order 0.4% of equity
across six ~1-lot positions on a $10k account — but it is a systematic bias in the
permissive direction, in a component whose whole job is to be conservative. Worth
either correcting or stating in the docstring as an accepted approximation.

## MINOR — the tests cannot fail on any of the above

Coverage of the two new pure functions is good. Coverage of the *seam* is not:
every controller-level case drives a `MARKET` decision
(`tests/unit/test_risk_manager_exposure_cap.py:178`) against a book that never
changes (`:190-227`). There is no case for a LIMIT/pending entry, none for two
signals inside one cycle, and none asserting the book-wide halt reaches an
operator. The suite is green and the cap is non-binding in production
simultaneously — which is the failure mode `CLAUDE.md`'s working-style section and
this repo's standing lesson ("never confirm on a green suite alone") warn about.
The remediation pass should land these three cases with the fixes.

## MINOR — the new fail-closed behaviour is undocumented outside the config comment

`CLAUDE.md`'s Risk/sizing bullet documents the sizing fail-safe contract precisely
because operators must know when and why Titan declines to trade. This session
adds a second, *global* fail-closed condition and leaves it recorded only in a
`config.yaml` comment. One line in `CLAUDE.md` (or a note in `docs/`) would keep
the authority docs true.

## Three-axis readiness

- **Does it work?** Partially. The two new functions do what their docstrings say
  and are well tested. The *feature* — a cross-symbol exposure cap — does not
  work in the shipped configuration: with a LIMIT-only strategy the aggregate the
  gate reads is `0.0` at every evaluation, and I reproduced an 11%-of-equity
  commitment passing a 5% cap with zero blocks logged.
- **Is it safe?** Two ways not yet. It is permissive where it must be strict
  (pending orders, in-cycle sends), and it is strict-but-mute where an operator
  needs to know (a single stopless or un-specced position silently stops all
  trading with no alert). The second is an availability risk on a live
  demo-forward test running unattended.
- **Is it maintainable?** Yes. Naming, docstrings, fail-safe idiom, config
  comment and test structure all match the surrounding code closely; the
  remediation surface is small and the data it needs is already persisted.

## Verdict rationale

The session's premise was real and the chosen shape (aggregate risk / equity,
checked at `_execute_signal`, fail-safe on unknowns) is the right one. But the
gate is wired to a data source that, for the only strategy Titan is allowed to
run, is empty precisely when the cap should be biting. Shipping it as-is would
record "cross-symbol exposure cap: DONE" against a control that has never once
been able to block a trade. That has to be fixed before this closes.
