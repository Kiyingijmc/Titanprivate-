## Adversarial checks

- **Bypass hunt**: only two sites ever set `_state[...] = "ACTIVE"` —
  `activate_eligible()` (honors the veto, untouched) and `enable()` (now vetoed).
  The Telegram path funnels through `registry.enable`; `enable_strategy`'s
  `_refresh_strategies_from_registry()` only re-reads registry state, so a vetoed
  call has zero side effects. No other activation path exists.
- **Defense in depth**: `BaseStrategy.__init__` sets `self.active = enabled` and
  `validate_data` returns False when inactive — with `enabled: false` the instance
  itself also refuses to signal even if state were somehow forced. Consistent.
- **Flip semantics not inverted**: fires iff `prev != 0 and sign != 0 and
  sign != prev` — genuine reversals only; flat suppression retained. Re-activation
  after disable/enable keeps `_prev_sign` memory, so behavior across
  suspend/resume is unchanged (no re-cold-start, no spurious fire).
- **`active_symbols` side effect of the config flip**: `system_controller.py:220`
  gates `pairs` seeding on `enabled`, but ma_slope_baseline has no `pairs` key in
  config (unscoped), so the flip changes nothing there.
- **Veto typing**: `is False` matches `activate_eligible()` exactly; YAML `false`
  → Python `False`. A string `"false"` would slip both checks equally — pre-existing,
  consistent, out of scope.
- **Out-of-scope files**: none touched. `activate_eligible()`, `disable()`,
  telemetry.py, trade management, risk code, manifest schema, other strategies —
  all byte-identical to main.
- **Message-precision nuance (not a defect)**: an ACTIVE strategy with
  `enabled: false` now gets the veto message instead of "illegal transition from
  ACTIVE" — placement is exactly what the spec dictated; unreachable in practice
  (a vetoed strategy can't become ACTIVE).
