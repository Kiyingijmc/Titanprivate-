## Does the fix actually work? (trace)

`tests/unit/test_research_run.py:199` pins `BTCUSD_SPEC = {"tick_size": 0.01, "tick_value":
0.01, "vol_step": 0.01}` into a tempdir fixture (`:205-206`) and passes it through the real
`--specs` flag (`:223`, `:227`), which is a genuine argument
(`scripts/research_run.py:359`) consumed on the single-symbol path
(`scripts/research_run.py:507-509`). `_load_specs` (`scripts/research_run.py:97-103`) reads the
file fresh on every call and caches nothing at module scope, so the fixture fully displaces the
`_DEFAULT_SPEC` fallback.

Sizing under the pinned spec (`tests/backtest/backtest_engine.py:148-170`): for a stop of `D`
dollars, `stop_ticks = D/0.01 = 100D`, `money_per_lot = 100D × 0.01 = D`. So
`lots = floor((1000/D)/0.01) × 0.01`, capped at 5.0 — non-zero for any stop below **$100,000**.
Silver-bullet H1 stops on a ~$91k instrument are hundreds of dollars, so `lots ∈ [~1, 5]` for
every trade. Costs therefore reach net R:
`spread_cost = spread_points × 0.01 × lots` → ~$0.05·lots (cheap, 5) vs ~$5·lots (expensive,
500), i.e. ~0.005·lots R of separation per trade after
`net_r = net / 1000` (`scripts/research_run.py:283`).

Spread does not affect trade *resolution* — `simulate_signals` runs before `trade_dollars`
(`scripts/research_run.py:275-284`), so both legs resolve the **identical** trade set and only
`r` is rescaled. Hence `expectancy` (`tests/backtest/backtest_engine.py:86-115`, TP/SL only) is
strictly greater for the cheap leg. Both final assertions
(`assertNotEqual` at `:246-249`, `assertGreaterEqual` at `:251-254`) hold, and hold
*deterministically* rather than as a function of workspace state.

The new guard at `:238-240` (`metrics.is.trades > 0`) is also safe: trade resolution is
spec-independent, and the backlog's own gate evidence records this test **passing** on a main
checkout with a real `specs.json` — which is only possible if the IS split contained TP/SL
trades. That count cannot change with the spec.

**Conclusion: the CRITICAL raised in the prior cycle (fixture pinned to the failing
`_DEFAULT_SPEC` values) is genuinely resolved.** The fix is hermetic, non-degenerate, and
minimal.

## Findings

### MINOR — the degeneracy guard's constants are hardcoded copies, so it can drift out of sync with the run it guards

`tests/unit/test_research_run.py:212-215` re-derives the sizing with literals: `risk_dollars=1000.0`,
`commission_per_lot=7.0`, and `trade_dollars`' implicit `max_lots=5.0`. The real run reads
`DEFAULT_RISK_DOLLARS` (`scripts/research_run.py:60`, `:283`) and pulls commission/max-lots from
`config/config.yaml` (`scripts/research_run.py:511-512`). The values agree *today*; nothing keeps
them agreeing. The probe also uses a fabricated `91000/90500` stop rather than any stop the run
actually produces, so it proves "this spec can size a $500 stop", not "this spec sizes these
trades".

**Failure scenario:** someone changes `DEFAULT_RISK_DOLLARS` from `1000.0` to a much smaller
basis (or `hard_max_lots` to `0`). The probe still asserts `lots > 0` and passes, the real run
sizes to zero lots, costs vanish from net R, and the test fails at `assertNotEqual` (`:246`)
with the same inscrutable "two expectancies are equal" message the probe exists to prevent.
The test still fails loudly — it just fails in the un-diagnosable way, so this is a
guard-quality regression risk, not a correctness bug.

**Cheap fix:** import `DEFAULT_RISK_DOLLARS` alongside `_DEFAULT_SPEC` (the module already
imports from `research_run` at `tests/unit/test_research_run.py:29-32`) and pass the config-read
`max_lots`/`commission_per_lot`, rather than magic numbers.

### MINOR — the explanatory comment's arithmetic is off by 100×

`tests/unit/test_research_run.py:210-211`: *"500 points of stop at $0.01/tick -> $500/lot"*.
With `tick_size = 0.01`, 500 points **is** $5.00 of price, which is $5/lot, not $500/lot. The
stop the probe actually uses is 500 *price units* = 50,000 ticks, which is where $500/lot comes
from. The stated results ($500/lot, 2.0 lots) are correct; the derivation bridging them is not.

**Failure scenario:** a maintainer sanity-checking `BTCUSD_SPEC` against this comment computes
$5/lot, concludes the spec is wrong by 100×, and "fixes" the constant back into a degenerate
range — reintroducing exactly the failure this session just closed. This comment is the sole
written justification for a magic constant, and the previous review cycle on this branch failed
precisely because the spec constants were reasoned about incorrectly.

Neither MINOR blocks the fix from working; both are one-line polish.

## Observations (not findings — outside this session's scope)

- **A real production silent-failure surfaced here and is recorded only in a test comment.**
  `scripts/research_run.py:61` applies a 5-digit-forex `_DEFAULT_SPEC` to *any* symbol missing

  `tests/unit/test_research_run.py:192-198`, where nobody editing `research_run.py` will see
  it. I am not editing `_BACKLOG.md` (orchestrator-owned) — flagging for whoever does.
- **The backlog prescribed "hermetic spec fixture + tearDown reset"; only the fixture was
  delivered.** I checked, and the `tearDown` half genuinely isn't needed: `_load_specs`
  (`scripts/research_run.py:97-103`) reopens the path every call and `trade_dollars` /
  `_signals_to_trades` take `spec` as a plain argument — there is no module-level mutable spec
