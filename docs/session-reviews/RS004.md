## Does it work?

**Hash chain (§1.1/§1.3).** `compute_row_hash` (`tradebot/core/event_log.py:149-168`) hashes
`prev_hash ‖ seq ‖ schema ‖ schema_version ‖ ts_event ‖ canonical_json(payload)` exactly as
`pass3-systems.md:30` specifies, with a `\x1f` separator (a strengthening — both write and
verify paths use the same function). `_append_locked` (`:426-518`) takes `BEGIN IMMEDIATE`
up front, re-derives the head from the last retained row, refuses to append when the
`log_meta` marker is ahead of the rows (`:458-465` — the mechanism that makes a lost tail
detectable), and commits row + marker atomically. `verify_chain` (`:546-630`) walks
gaplessness, genesis `prev_hash`, per-row linkage, payload decodability, `row_hash`
recomputation, sidecar hashes, and tail-vs-marker agreement, raising `RecoveryRequired` on
any break — never a soft or partial result. Faithful to §1.3.

**The five corruption drills** — the M0 acceptance bar cited in both `_BACKLOG.md:16` and
`pass8-synthesis.md:225`(a) — are in `TestCorruptionDrills`
(`tests/unit/test_tradebot_event_log.py:227-331`): truncate (`:239-256`, including a second
case proving a truncated log also refuses further *appends*), payload bit-flip (`:258-269`),
`row_hash` bit-flip (`:271-279`), deleted middle and first row (`:281-295`), and corrupt
sidecar in all three failure shapes — tampered-but-valid-gzip, damaged stream, missing file
(`:297-324`), with a restore-and-reverify tail proving the drill measured the sidecar and
not some unrelated breakage. I traced each to its intended `RecoveryRequired` branch; none
can produce a clean boot. This is the session's headline deliverable and it is solid.

**Determinism** (`TestDeterminism`, `:196-224`) proves identical streams under *different*
ingest clocks produce byte-identical chain heads, and that a differing payload diverges the
head — pass8 M0 acceptance (b), discharged.

**Backup + restore-verify.** The prior review's CRITICAL — a backup that never captured the
snapshot sidecars, masked by a verification that read the still-present *live* directory —
is genuinely fixed, not papered over. `backup_and_verify` now emits two artefacts and
bundles the sidecars (`:855`, `:870`, `_bundle_sidecars` at `:1012-1032`); `verify_backup`
extracts that bundle into the temp workdir and points the probe at it (`:914-929`), so the
live directory is never consulted. `_unbundle_sidecars` (`:1035-1057`) rewrites members by
hand rather than `extractall`, rejecting absolute paths, `..`, symlinks and devices — an
unprompted and correct hardening. The regression guard that matters,
`test_restore_succeeds_with_the_live_snapshot_directory_destroyed` (`:584-597`), destroys
`snapshots/` before verifying and would have failed against the old code. Six further tests
cover missing bundle, tampered member, damaged container, no-sidecar logs, tampered row,
and backing up an already-broken log.

## Findings

### MAJOR — `archive_before` can delete live events from SQLite without writing them to Parquet, when the target month file already holds *different* events at the same `seq`

`tradebot/core/event_log.py:790-820` runs three steps: read the eligible rows, write them
via `_write_parquet`, then `DELETE FROM events WHERE seq<?` and bump `archived_through_seq`.
The remediation made step 2 idempotent by dropping any offered row whose `seq` is already
present in the target file (`:1105-1112`):

```python
already = set(existing.column("seq").to_pylist())
if already:
    fresh = pa.array([seq not in already for seq in columns["seq"]], type=pa.bool_())
    table = table.filter(fresh)
```

The dedup key is `seq` **alone**. `row_hash`, `event_id` and `source_db` are never compared,
even though all three are right there in the row. For the crash-retry case the method was
written for that is correct and safe (the re-offered rows are byte-identical). For any case
where the pre-existing file holds a *different* history at those seqs, the rows are silently
discarded — and step 3 deletes them from SQLite anyway, unconditionally.

**Failure scenario.** An operator hits `RECOVERY_REQUIRED`, and does the obvious thing:
moves the unrecoverable `data/events.sqlite3` aside and starts a fresh log. The default
archive directory is `db_path.parent / "archive"` (`:788`) — a sibling of the DB file, so it
survives untouched, still holding `events-202603.parquet` from the old log with seq 1…N.
The new log accumulates events in the same calendar month, snapshots twice, and the nightly
archive job runs. `verify_chain()` passes (the *live* chain is internally perfect; the
Parquet file is external state it never inspects). `_write_parquet` sees seq 1…N already
present and filters every new row away, rewriting the old file unchanged. `archive_before`
then deletes those rows from SQLite and advances the watermark. The events are now in
neither place — permanently lost from the money-truth trail — and the method returns
`{"rows": N, "files": [...], "archived_through_seq": N}` (`:823-827`; `rows` is `len(rows)`
*offered*, and `_write_parquet` returns `None`, so nothing anywhere reports that zero rows
were actually written). No exception, no `RecoveryRequired`, no log line — the module has no
logging at all, so `RecoveryRequired` is its only ops signal, and this path doesn't raise it.

The same shape is reachable whenever two logs share an archive directory, and — more
subtly — it is the reason the DR case in the next finding is undetectable.

This directly contradicts the module's governing rule as its own docstring states it
(`:8-12`: "the log is either provably intact or it says `RECOVERY_REQUIRED`"), and
`_write_parquet`'s docstring claims the idempotency as a safety property (`:1070-1077`)
without noting that it holds only when the colliding rows are identical — which nothing
checks. Note also that the remediation *introduced* this: the pre-remediation code would
have duplicated the rows (visible, recoverable) rather than dropped them (silent,
unrecoverable).

**Suggested fix:** compare `row_hash` for colliding seqs — identical ⇒ drop (the intended
retry idempotency); different ⇒ raise `RecoveryRequired`, since a live chain and an archive
that disagree at the same `seq` is exactly the "not provably intact" condition this module
exists to announce. Also return the written-row count from `_write_parquet` and report it in
`archive_before`'s result dict, so a no-op retry is distinguishable from a real archive.

### MINOR — the archive↔live seam is never hash-anchored: `chain_last_row_hash` is written into the Parquet metadata and then never read by anything

After an archive, `verify_chain` anchors the retained log on a *seq* watermark only
(`:575`: `expected_first = max(from_seq, archived_through + 1)`), and the genesis check is
guarded by `seq == 1` (`:586-587`). So for a log that has been archived, the first retained
row's `prev_hash` is compared against nothing at all — it is accepted as given.
`archive_before` persists only `_META_ARCHIVED_THROUGH`, a seq (`:812`), while
`_write_parquet` computes and stores `chain_last_row_hash` in the Parquet schema metadata
(`:1125`) that no code in this module ever reads back. `verify_chain(from_seq=N)` has the
same hole by construction, and that parameter's intended caller is exactly M0-4's
`verify_and_replay`, which `pass3-systems.md:113` specifies as "walk chain from snap.seq to
head" — so the gap is about to be load-bearing.

**Failure scenario:** the two halves of the log (Parquet archive and live SQLite) can be
mismatched — including by the MAJOR above — and every verification path in the module still
reports clean, because nothing ever asserts that the retained chain continues the archived
one. Cheap fix, and it closes both findings: store `archived_through_row_hash` in `log_meta`
at archive time, and have `verify_chain` require `rows[0].prev_hash == ` that value whenever
`archived_through > 0` (and `_write_parquet` cross-check it against the target file's own
`chain_last_row_hash`).

### MINOR — snapshot sidecars are never archived or pruned, so every nightly backup re-tars the entire history of them

`archive_before` moves `snapshot.projection` rows into Parquet and deletes them from SQLite
(`:790-819`) but leaves their sidecar files in `snapshots/` untouched, and the Parquet
artefact carries only the event row, not the sidecar bytes. Meanwhile `_bundle_sidecars`
(`:1019-1032`) tars *every file in the directory* on every backup (`:870`).

**Failure scenario (a):** with the default cadence (10 000 events / 24 h) and projections
over the 256 KB inline limit, sidecars accumulate one per snapshot forever; the nightly
`events-<stamp>.snapshots.tar.gz` therefore grows monotonically with the log's total
lifetime rather than with retained state, and the off-box ship §1.3 calls for grows with it.
**(b):** if an operator ever prunes `snapshots/` to reclaim that space, every archived
snapshot event in Parquet becomes unreconstructable, and — because those rows are no longer
in SQLite — no `verify_chain` will ever notice. Not urgent, and §1.3 does not explicitly
assign sidecar retention to this module, but it is the one remaining place where the
sidecar story is incomplete now that the backup half is fixed.

  and explained in the module docstring (`:17-22`): a test package named `tradebot` would
  shadow the real top-level package under `unittest discover`. Same precedent as S003.

## Three-axis readiness

- **Does it work:** the acceptance bar this session was graded against — the five drills,
  plus determinism — is met and traced clean, and the backup half is now genuinely
  disaster-correct. The archive half has one silent data-loss path (MAJOR) and one missing
  cross-half anchor (MINOR), neither exercised by the committed suite. Unrun `VERIFY_CMD` is
  an open item, not a finding.
- **Is it safe:** additive only, confined to `tradebot/` plus one test-hygiene fix; no
  existing Titan v14 code touched; no new environment dependency. Safe on a branch. The
  backup job's `verified: True` can now be trusted; `archive_before`'s success report cannot.
- **Is it worth it:** yes. This is a careful, well-tested implementation of the F-004
  substrate, and the remediation pass fixed the prior CRITICAL properly (behaviour + a guard
  test that fails against the old code) rather than cosmetically. The remaining work is
  narrow and lives entirely inside `archive_before`/`_write_parquet`.

## Verdict

The corruption drills, determinism, and the repaired backup/restore-verify path all hold up
under trace. What does not is the archive: making the Parquet write idempotent by `seq`
alone converted a visible duplication bug into a silent deletion one, and there is no hash
anchor tying the archived prefix to the retained chain that would let anything notice. For
the module whose stated single rule is "provably intact or `RECOVERY_REQUIRED`", a path that
drops money-truth events and reports success needs one more pass — a small one, in the two
methods named above.
