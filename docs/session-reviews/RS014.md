## Premise check — the crash mode was real

Not assumed. I read uvicorn's actual `Config.bind_socket()`
(`.venv/lib/python3.12/site-packages/uvicorn/config.py:538-576`): on a bind
`OSError` it calls `logger.error(exc); sys.exit(1)` (line 576) — no
catchable exception, a `SystemExit`. Before this session, `server.py`'s
`start()` called `asyncio.create_task(server.serve())` with no explicit
sockets, so `Server.startup()` (`uvicorn/server.py:104-`) would reach
`config.bind_socket()` internally. A `SystemExit` raised inside a
fire-and-forget `asyncio.Task` is not caught by the caller's
`except Exception` in `system_controller.py`'s old inline block — `Exception`
does not catch `BaseException`/`SystemExit` — so a port collision (e.g. the
known `gui_demo_server.py` squatter) would propagate past the task boundary
into the event loop, exactly matching the outage this session exists to
prevent. Premise confirmed against the actual dependency source, not the
commit message's word for it.

## What the diff does

`src/ops/web/server.py`:
- New `_bind_socket(host, port)` (`:130-147`) binds + listens **synchronously**
  in plain Python before uvicorn ever sees the socket, so a bind failure
  raises a plain `OSError` right there, closing the socket first.
- `start()` (`:150-160`) now reads `TITAN_GUI_PORT` (default `8770`, new — the
  session's config knob), calls `_bind_socket`, and passes
  `server.serve(sockets=[sock])` instead of a bare `serve()`. I confirmed in
  `uvicorn/server.py:124-145` that when `sockets` is supplied, `startup()`
  skips `config.bind_socket()` entirely and hands the pre-bound socket
  straight to `loop.create_server(sock=...)` — the `sys.exit(1)` path is
  provably bypassed, not just hoped around.

`src/core/system_controller.py`:
- The inline `try/except` block in `run()` is extracted verbatim into
  `_start_gui()` (`:246-264`) with a docstring recording *why* (`except
  Exception` needed something synchronous and catchable to catch, which is
  exactly what the new `start()` now provides). `run()` calls `self._start_gui()`
  (`:306`) in its place — a pure refactor at that call site, diff confirms no
  duplicated block was left behind.

`tests/unit/test_gui_server.py` (purely additive — `git diff a852681..HEAD
--numstat -- tests/` is `174/0`, no pre-existing assertion touched):
- `TestStartBindFailure` occupies a real port and asserts `start()` raises
  `OSError`, explicitly `assertNotIsInstance(..., SystemExit)`.
- `TestControllerGuiBootSeam` drives the actual `SystemController._start_gui`
  (via `object.__new__` + hand-set `root_dir/config/logger/bus`) against an
  occupied port and asserts boot continues, `_web_task is None`, and a
  `WARN/GUI` log line exists.
- `TestGuiPortEnv` (rewritten in `3add570`) asserts the bind by spying on
  `_bind_socket` and reading `getsockname()` off the socket it returned, rather
  than the original version's blocking `socket.create_connection(timeout=1.0)`
  loopback round-trip inside the coroutine — which the commit message
  documents pinned the event loop and produced a 1.0s hard deadline that a
  loaded box (the full-suite run) could miss even though the production path
  was correct.

## Findings

**None actionable at MAJOR/CRITICAL.** One cosmetic MINOR:

- **`system_controller.py:261`** — the success log is a hardcoded literal:
  `self.logger.log_event("INFO", "GUI", "Control API on :8770")`. This
  session is what makes the port configurable (`TITAN_GUI_PORT`, new in
  `server.py`), so if an operator sets `TITAN_GUI_PORT` to anything other than
  `8770`, the boot log will confidently report the wrong port. Not a safety or
  correctness defect — the bind itself uses the right port — but it's an
  operator-facing observability regression introduced by this session's own
  feature, on a project whose `CLAUDE.md` explicitly cares about logs being
  trustworthy (the portfolio-cap section: "otherwise a total trading stop is
  indistinguishable from a quiet market"). Cheap to fix (interpolate `port` or
  drop the literal), not worth blocking on.

## Three-axis readiness

- **Does it work?** Yes. Verified against uvicorn's actual source that the
  `sys.exit(1)` path is bypassed when `sockets=` is supplied, and both the
  targeted GUI suite (14/14) and the full 677-test suite pass clean.
- **Is it safe?** Yes. The failure mode this session closes is a
  `SystemExit` escaping an `asyncio.Task` and crashing the event loop — i.e.
  the whole trading bot — on nothing more than a stray process holding
  `:8770`. It's now a plain, caught `OSError` that logs a `WARN` and leaves
  trading untouched (`_web_task = None`), matching the "must never block
  trading" contract this project holds the GUI subsystem to.
- **Is it worth it?** Yes. This directly targets a class of failure the
  operator's own demo-forward-test already hit in production. The fix is
  minimal (one new synchronous-bind helper, a one-line call-site refactor,
  purely additive tests) and does not touch the read-only/mutation/auth
  surface of the GUI API at all.

The production change is sound, verified against the actual third-party
source it depends on rather than taken on the commit message's word, and
backed by a full green suite plus tests that provably die if the fix is
reverted. The one MINOR finding is a log-message accuracy nit, not a defect
in the fix itself.
