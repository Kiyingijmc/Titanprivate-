## Premise check — the defect was real, and the trace pins the mechanism exactly

Not taken on the prompt's word. The production evidence is
`data/logs/titan_live_stdout.log:29-77` (one occurrence, `grep -c` = 1, matching
the spec's own downgrade from the drafted "5x/2h"). The tail of that traceback is
what makes this reviewable rather than plausible:

```
  File ".../src/ops/web/server.py", line 96, in ws
    await websocket.close(code=1008)
  File ".../starlette/websockets.py", line 86, in send
    await self._send(message)
  File ".../uvicorn/protocols/websockets/websockets_impl.py", line 342, in asgi_send
    raise RuntimeError(
RuntimeError: Unexpected ASGI message 'websocket.close', after sending 'websocket.close' or response already completed.
```

Two facts fall straight out of those frames, and both matter for judging the fix:

1. **`starlette/websockets.py:86`** is inside the `elif self.application_state ==
   WebSocketState.CONNECTED:` branch of `WebSocket.send()`. So at the moment of
   the crash `application_state` was **CONNECTED**, not DISCONNECTED. The spec
   offered the builder a choice — "check `websocket.application_state`/
   `client_state`". A guard on `application_state` would have been a no-op and
   would **not** have fixed this bug. The builder picked `client_state`
   (`src/ops/web/server.py:99`), which is the correct one.
2. **`websockets_impl.py:342`** is the final `else:` of `asgi_send` — reached
   because `self.closed_event` was already set. The only way it gets set during a
   pending auth `receive_text()` is `asgi_receive`'s
   `except ConnectionClosed: self.closed_event.set()` (`websockets_impl.py:364-365`),
   which in the same breath returns `{"type": "websocket.disconnect"}`. Starlette's
   `WebSocket.receive()` consumes that message and sets
   `self.client_state = WebSocketState.DISCONNECTED` (`starlette/websockets.py:54`)
   before raising `WebSocketDisconnect`.

So uvicorn's `closed_event` and starlette's `client_state == DISCONNECTED` are set
by *the same message delivery* on this code path. The guard at
`server.py:99` therefore provably covers the observed trace — this is a
source-level derivation, not an inference from the test passing.

## The fix

`src/ops/web/server.py:98-109`:

```python
        if not auth.token_ok(token):
            if websocket.client_state != WebSocketState.DISCONNECTED:
                try:
                    await websocket.close(code=1008)
                except RuntimeError:
                    _LOG.debug("WS auth-reject close raced an already-closed "
                               "connection", exc_info=True)
            return
```

`return` sits at the outer indent level, so every reject path still returns —
no fallthrough into `send_json`/`bridge.attach()` was introduced. On a live
connection (`client_state == CONNECTED`) the `close(code=1008)` is byte-for-byte
the previous behaviour, so the normal reject and successful-auth paths are
untouched. New `logging` import + module `_LOG` are the only other additions.

## The three operator concerns — adjudicated

**(1) "The test is circular — it patches `close` to raise exactly when
`client_state == DISCONNECTED`, the same condition the fix guards on."**
*Refuted, on source evidence.* The circularity would only matter if the mock's
trigger condition were an invention of the fix's own theory. It is not: as
derived above, uvicorn raises on this path precisely when `closed_event` is set,
and `closed_event` is set by the same `asgi_receive` call that drives starlette's
`client_state` to DISCONNECTED (`websockets_impl.py:364-365` →
`starlette/websockets.py:54`). The stub's condition is the real condition. The
docstring's claim that this "fakes the same state ... without needing a real
uvicorn socket" is accurate, and the frame numbers in the production log
corroborate it independently of the test.

**(2) "With the guard in place the `except RuntimeError` may be unreachable —
shipped but never exercised."** *Half true, and I'd call it belt-and-braces
rather than dead code.* The guard reads starlette's application-level
`client_state`; the RuntimeError comes from uvicorn's transport-level
`closed_event`. Those two can diverge: on the
`asyncio.wait_for(..., _WS_AUTH_TIMEOUT_S)` **timeout** path the inner receive is
cancelled, so if `ConnectionClosed` fired inside `asgi_receive` at the instant of
cancellation, `closed_event.set()` has run but the `websocket.disconnect` message
was discarded by the cancellation — `client_state` stays CONNECTED and the
subsequent `close()` still raises. The same holds for the other WS backends
(`wsproto_impl.py:451`, `websockets_sansio_impl.py:470`), whose state bookkeeping
differs. So the branch is reachable in production, narrowly. It is, however,
**not exercised by any test**: with the shipped guard the stub's raise condition
is never met. See MINOR-1.

**(3) "The bare `except Exception` still swallows `WebSocketDisconnect` into
`token=None`; the fix does not address that."** *Correct as an observation,
correctly out of scope as a defect.* §2 says "Distinguishing those two is in
scope", contrasted against "changing what counts as a valid token is not" — that
sentence delimits the permitted blast radius, it does not mandate the work, and
§4's testable checklist contains no line item for it. More to the point, the
conflation has **no operator-visible consequence today**: the reject path emits no
log, no metric and no counter, so a clean disconnect misread as a bad token is
indistinguishable from a bad token *and nothing observes either*. The one thing
that did make the conflation visible — the ASGI traceback — is exactly what this
session removes. Not a finding.

## Findings

No CRITICAL. No MAJOR. Nothing a remediation pass must address.

**MINOR-1 — the `except RuntimeError` branch (`server.py:102-108`) ships with
zero coverage.** The added test can never enter it: `flaky_close` raises only
when `client_state == DISCONNECTED`, which is precisely when the guard skips the
call. I confirmed this by mutation — inverting the guard to
`if websocket.client_state == WebSocketState.DISCONNECTED:` leaves
`test_close_after_client_disconnect_does_not_raise` **passing**, because the
`except` then catches what the guard used to prevent. The test therefore pins the
*invariant* ("the reject path does not propagate RuntimeError") rather than
either mechanism — which I consider the right thing to pin, and why this is MINOR
and not a blocker. The uncovered branch's failure mode is a return to the
original cosmetic log noise, with no trading impact.

**MINOR-2 — regression in the guard would surface as a suite hang, not a test
failure.** Under the same inverted-guard mutation, a live-connection reject stops
closing, and `test_wrong_first_frame_closes_1008` (`tests/unit/test_gui_server.py:190-196`)
does not fail — it **wedges** on `ws.receive_json()` and had to be killed:

```
test_wrong_first_frame_closes_1008 ... EXIT=124   # timeout 100, no verdict
```

This is a pre-existing property of that test (this session did not write or
modify it), but this session is what makes the close *conditional*, which widens
the set of edits that can trip it. On this project specifically that is worth
recording, because the standing operator lesson is that `rc=124` from
`VERIFY_TIMEOUT` is a slow suite and *not* a failure — so a real regression in
this exact guard would arrive wearing the one costume the team has trained itself
to dismiss. A bounded `assertRaises` with a receive timeout would convert the
hang into a verdict. Cheap, not blocking, and arguably belongs to whoever owns
that older test rather than to S015.

## Non-blocking observations (no action required)

- `src/ops/web/server.py:11` and `tests/unit/test_gui_server.py:11` are the
  repo's **first direct `starlette` imports**, and `starlette` is not listed in
  `requirements.txt` (it arrives only as FastAPI's transitive dependency).
  `fastapi.websockets` re-exports `WebSocketState`, so
  `from fastapi.websockets import WebSocketState` would have kept the module's
  existing single-source import convention (`from fastapi import ... WebSocket,
  WebSocketDisconnect`) with no behaviour change. Cosmetic; CLAUDE.md's
  "ask before adding new dependencies" is not engaged, since nothing new is
  actually being depended on.
- The guard catches `RuntimeError` only. Starlette's `send()` converts an
  `OSError` from the transport into `WebSocketDisconnect`
  (`starlette/websockets.py:86-88`), and uvicorn's `ClientDisconnected` *is* an
  `OSError` (`uvicorn/protocols/utils.py:10`), so a disconnect landing during the
  close write would escape as `WebSocketDisconnect` and still produce an
  "Exception in ASGI application" traceback. In practice `websockets`' `close()`
  is idempotent and does not raise `ConnectionClosed`, and the spec explicitly
  named `RuntimeError`, so this is a theoretical residue, not a gap. It cannot
  reach the trading engine either way — uvicorn's `run_asgi` absorbs it.
- No `assertLogs` on the new `_LOG.debug` line, so the log message itself is
  unverified. Immaterial at debug level.

## Three-axis readiness

- **Does it work?** Yes. The guard is provably on the correct state attribute for
  the observed trace (derived from the starlette/uvicorn source and the
  production frame numbers, not from the commit message), the targeted module is
  16/16 green, and the added test errors with the exact production exception when
  the guard is removed.
- **Is it safe?** Yes. The change is strictly subtractive on the failure path —
  it removes a raise — and byte-identical on the normal reject and successful-auth
  paths, both of which retain passing assertions. It touches no trading, risk,
  execution or bridge code; `.mig/config RISKY_DOMAINS` is not engaged. It is
  aligned with the sibling S014 contract that a GUI fault must not reach the
  engine.
- **Is it worth it?** Yes, modestly, and the spec is honest about the modesty: one
  confirmed occurrence, log hygiene only, no functional impact on trading. The
  cost is 14 lines and one test, with no scope creep — the builder did not take
  the §2 invitation to refactor the `except Exception` conflation, which on this
  project's history is the right call.

The fix is minimal, correct for the right reason, provably regression-guarded,
and scoped exactly to the two files the spec named. The two MINOR items are
test-coverage observations, not defects in the shipped behaviour.

MIG-VERDICT: PASS
