## Findings

### MAJOR — residual sweep race: a PENDING row registered between heartbeats is still lost if the 60 s recon tick lands in that window

The fix corroborates against `current_pending_orders`, which is a snapshot
rebound only on HEARTBEAT — and the EA heartbeats every 5000 ms
(`Titan_Gateway.mq5:98`). A row registered by `EXECUTION:OPENED` is
uncorroborated until the *next* heartbeat arrives (≤5 s, avg ~2.5 s).
`reconcile_state` has no grace period (`state_manager.py:169-182` selects
every row, no `time_placed` filter), and the recon gate is checked at the top
of every loop iteration (`system_controller.py:313-315`), so a 60 s tick can
interleave between the drain that processed the OPENEDs and the drain that
processes the next heartbeat. Repro (real StateManager, real
`_perform_reconciliation`):

```
OPENED registers PENDING #222; last heartbeat predates the order
pendings after recon-in-window: []
telegrams: ['⚠️ **Sync Guard:** Resolved Ticket `#222` (Closed externally)']
```

Odds ≈ window/interval ≈ 2.5–5 s / 60 s ≈ **4–8 % per signal bar**, and it is
all-or-nothing per bar: every limit of one sweep registers in the same drain,
so when the tick lands badly the *entire batch* is falsely swept. Unlike a
falsely-swept ACTIVE row — which the heartbeat `pos` loop re-adopts within
5 s (`system_controller.py:713-720`) — **nothing re-registers a swept PENDING
row** (the heartbeat's `orders` rows carry no `sl`, so they can't be priced or
re-registered). Consequences per occurrence, for the order's entire resting
life (up to 12 h on H1): the cap under-counts that bar's full batch (round 2's
symptom, now stochastic), the 12-bar TTL cancel is dead for those orders (a
stale limit can fill hours later, outside the validated setup window —
`_cleanup_ghost_orders` iterates DB rows only), and the operator gets false
"Closed externally" Telegrams. Note also that round 2's proposed shape (a)
("exclude PENDING rows from the sweep") would have failed in the over-count
direction; the chosen union shape fails in the under-count direction — the one
this component is documented to refuse.

This race *class* is pre-existing on `main` (identical window for ACTIVE
rows), but there it self-heals in ≤5 s; here it does not, and it sits in the
exact seam this session's Definition of Done depends on. Fix is small: make
`reconcile_state` (or the caller) skip rows whose `time_placed` is younger
than a grace window (e.g. 15 s ≥ 3× the heartbeat period), plus one seam test
each way (fresh row + stale snapshot survives; row older than grace with no
corroboration sweeps). Do not fix by re-registering from heartbeat `orders`
(no `sl` — can't be priced).

### MINOR — a STOP entry order would register ACTIVE and be invisible to the cap while resting

`reg_status = "PENDING" if meta['cmd'] == "LIMIT" else "ACTIVE"`
(`system_controller.py:628`): a resting STOP entry gets an ACTIVE row — not
in `get_pending_orders()` (status filter), not in the heartbeat `pos` list —
so its risk is invisible to the aggregate until fill. Latent today
(SilverBullet emits only LIMIT, and near-market LIMITs convert to MARKET),
but the new docstrings and `config.yaml` comment claim "resting LIMIT/STOP
entries" are counted, which overstates. Either widen `reg_status` to cover
`STOP` or narrow the claim to LIMIT.
