### CRITICAL-1 — the sweep deletes the DB row on an **unconfirmed** cancel, re-introducing RS022 MAJOR-1 in the same file, 200 lines away from its fix

**Evidence** — `src/core/system_controller.py:708-710`:

```python
ticket = o['ticket_id']
await self.bridge.send_command("CANCEL", {"ticket": ticket})
self.state_manager.delete_order(ticket)
```

`ZMQBridge.send_command` is fire-and-forget on PUSH and **returns `False` on a wire
error** (`src/execution/bridge_zmq.py:74-81`). That return value is discarded at
`:709`, and `delete_order` runs unconditionally at `:710`. An EA-side rejection
(retcode 10018, market closed) never reaches Python at all.

This is the exact pattern the immediately preceding session was remediated for. The
corrected convention is in this same file, and its docstring already spells out why:

> `_sweep_pendings_on_breaker_trip`, `:944-951` — *"Deleting the DB row on the strength
> of the send alone loses orders (RS022 MAJOR-1) … Nothing can re-register a swept
> PENDING row (state_manager.py:233), so a still-live order whose row was deleted
> becomes exactly the untracked pending the portfolio cap is documented as blind to —
> **worse than before the sweep existed**."*
>
> `:953-956` — *"So this follows the project's verify-from-HEARTBEAT convention: keep
> the row, re-send the cancel on every tripped heartbeat, and only forget the row once
> the broker stops reporting the ticket in the heartbeat's `orders` list."*

The new sweep's docstring cites the **legacy** `_cleanup_ghost_orders` as its
precedent instead (`:690-695`, "mirrors its CANCEL + delete_order pattern, including
its known limitation"). Consciously copying the pattern a review has already rejected
does not make it correct — and `_cleanup_ghost_orders` is materially safer, because it
only ever touches rows that are already 12 bars stale.

**Failure scenario (concrete).** EURUSD SilverBullet LIMIT #111 rests; a red-folder
USD event enters the 60 min pre-window; the sweep fires at `second == 0`; the EA is
wedged / the PUSH socket errors / MT5 refuses the cancel. Then:

1. `send_command` returns `False`, or the EA silently rejects. **The order is still
   resting at the broker.**
2. `delete_order(111)` removes the only record Titan has of it.
3. Nothing can ever cancel it again — every remover in the file is row-driven:
   this sweep (`:701`), `_cleanup_ghost_orders`' TTL (`:1362-1364`), and
   `_sweep_pendings_on_breaker_trip` (`:971`) all iterate `get_pending_orders()`,
   which reads `active_orders WHERE status='PENDING'` (`state_manager.py:307-311`).
   `state_manager` cannot re-register a swept row.
4. The order **fills into the release** — the precise event this session exists to
   prevent. The protective action produced the outcome it was written to stop.
5. The book-wide risk cap loses it: `aggregate_open_risk` sources resting risk from
   these same rows (`src/risk/risk_manager.py:428`; CLAUDE.md: *"Titan-placed resting
   pending orders (their state-DB rows)"*). The cap now under-counts and will admit
   further positions across the release.
6. If the DD breaker is also tripped, `_dd_breaker_cancel_sent` keeps a stale entry for
   a ticket whose row is gone: its "CANCEL confirmed" notice (`:981-986`) can never
   fire, and the breaker loses its handle on the order too.

**Why I rate this above RS022's MAJOR-1.** The breaker sweep only fires on a DD trip.
This one fires on any blocked symbol — and `check_symbol` returns blocked for **every**
symbol whenever the calendar is globally stale (`src/analysis/news/manager.py:108-110`)
or the gate faults (`system_controller.py:658-661`, pinned by
`test_gate_fault_pulls_the_book`). One transient `check_symbol` exception therefore
cancels-and-deletes the **entire** resting book in a single 60 s tick. A cold start or
a corrupt cache file makes `store.age()` return `None` → `is_stale` → same result
(`store.py:29-33`, `policy.py:126-128`), before a single red-folder event has been shown
to exist.

**Remediation direction** (mirror `:937-1000`, do not re-invent):
- Do not delete on send. Track sent tickets in a dict; delete only once the ticket
  stops appearing in the heartbeat's `orders` list (`self.current_pending_orders`,
  maintained at `:1349` and available at the 60 s tick).
- Respect `send_command`'s `False` — keep the row, retry next tick, escalate after N
  unconfirmed sends (`DD_CANCEL_ESCALATE_AFTER_SENDS` is the existing precedent).
- Announce the confirmed pull, not just the attempt (RS022 MINOR-3's lesson).
- Because the row now survives, the per-order Telegram at `:714-719` must be
  edge-triggered (one per ticket), or a stuck cancel will emit a message every 60 s.

**Test gap:** nothing pins any of this. RS022's three regression tests
(`test_row_is_deleted_only_once_the_broker_stops_reporting_it`,
`test_unsent_cancel_keeps_the_row_and_is_retried`,
`test_cancel_that_did_not_take_is_resent_on_the_next_heartbeat`) have no analogue here;
`_SweepBridge.send_command` (`test_controller_news_gate.py:63-65`) always returns `True`,
so the failure path is untestable with the current double.

### MAJOR-1 — no `filled` guard: a limit that filled seconds before the sweep loses the DB row of a **live position**

**Evidence** — `_sweep_news_blocked_pendings` (`:701-710`) iterates PENDING rows and
cancels/deletes with no check against open positions. The breaker sweep does exactly
that check, and RS022 MINOR-4 exists because it originally did not:

```python
# :974-975
if ticket in filled:
    continue  # already a position; not ours to cancel or delete
```

**Failure scenario.** LIMIT #111 fills at 14:59:57. The `PENDING → ACTIVE` flip happens
in the heartbeat adoption path (`:1340-1345`), i.e. on the next EA heartbeat (~5 s). The
sweep fires at 15:00:00 while the row still reads PENDING, the symbol is inside a
red-folder window, so it sends a doomed CANCEL and deletes the row of a **now-open
position**. Consequences:

- `TradeManager` never manages it — in-trade management only engages when
  `active_orders.initial_entry/initial_tp` are non-zero (CLAUDE.md; `docs/TRADE_MANAGEMENT.md`),
  and the row is gone. No BE at 38.2 %, no partials, no ratchet.
- The risk cap cannot count it; the Sync Guard has nothing to reconcile against.
- This is the 2026-08-03 stopless-GBPJPY incident class: a live, unmanaged position that
  every ordinary health check reports as fine.

The window is narrow (one heartbeat interval), but it is *widest exactly when it
matters* — fills cluster on the volatility this sweep is reacting to — and the fix is
one condition against `self.current_open_positions`, which the controller already holds.

**Test gap:** no analogue of RS022's `test_ticket_that_filled_is_left_to_the_adoption_path`.

### MAJOR-2 — the operator Telegram asserts a red-folder window that, in two of the three paths that trigger it, does not exist

**Evidence** — `:714-719`, sent for every pulled order regardless of `reason`:

> *"Reason: `{reason}`\nNot a TTL expiry — **the symbol entered a red-folder window while
> the order was still resting.** The strategy re-signals after the window if the setup
> still qualifies."*

Three distinct conditions reach that line, and only the first makes the sentence true:

| Trigger | `reason` the message quotes | The message's own claim |
|---|---|---|
| Real blocking event (`policy.blocking_event`) | `"USD Core PCE in 20m"` | correct |
| Gate fault (`:660`) | `"news gate fault, failing closed: feed exploded"` | **false** — no window; the gate is broken |
| Stale calendar (`manager.py:108-110`) | `"News calendar is stale (…) — trading halted"` | **false** — no window; the feed is unreachable |

In the two failure paths the body contradicts the `reason` it printed one line earlier,
and it promises "the strategy re-signals after the window" when there is no window to
end — the actual precondition is an operator fixing a feed. This matters precisely
because those are the cases where the operator most needs a correct diagnosis: this is
the same "a fail-safe that stops trading must be louder than what it protects against"
argument the session itself makes for `_alert_news_gate_fault` (`:665-669`), applied
inconsistently 40 lines later.

The session's own test only checks the message is *not worded like* the TTL cleaner
(`test_operator_notice_is_worded_apart_from_the_ttl_auto_clean` asserts
`assertNotIn("Auto-Clean")`), so the false claim is unguarded.

**Remediation:** branch the explanatory sentence on whether `reason` came from a real
event or from a fail-closed condition. A test that drives the fault path and asserts
the body does **not** claim a scheduled event would pin it.

### R2-MINOR-1 — the "fresh heartbeat" proof is not heartbeat-specific: any EA message re-arms it, and `_reboot_terminal` fabricates it

**Evidence.** `_news_feed_is_fresh` (`src/core/system_controller.py:734-741`)
claims:

> *"True while EA traffic is recent enough that `current_pending_orders`
> describes the broker's book NOW."*

It reads `self.last_heartbeat_time`. But that attribute is stamped at the very
top of `_process_incoming_data`, **before** the type dispatch —

```python
# :1402
self.last_heartbeat_time = datetime.now()
msg_type = msg.get('type')
```

— so a `TICK`, a `HISTORY`, or an `EXECUTION` re-arms it. Meanwhile
`current_pending_orders` has exactly one writer, the HEARTBEAT branch
(`:1526-1527`). And `_reboot_terminal` sets it with **no message at all**
(`:1599`), which matters on this host: `taskkill`/`terminal64.exe` are
Windows-only and no-op on Linux (CLAUDE.md), so the watchdog re-stamps every
~60 s during an outage while doing nothing about it.

The name is inherited, so the slip is understandable — but the guard's whole job
is to certify one specific field, and it certifies a different one.

**Reproduction** (run against the committed tree, using the session's own test
harness; script removed afterwards):

```
stale feed  -> _news_feed_is_fresh(): False
after TICK  -> _news_feed_is_fresh(): True  (current_pending_orders untouched: [{'t': 111}] )
deleted rows: [222] | rows left: [111]
#222 is STILL RESTING at the broker and its DB row is gone
```

The second half drives the sweep: the last real HEARTBEAT listed only `#111`;
`#222` was registered PENDING afterwards by an `EXECUTION:OPENED`, so it has
never appeared in `orders`. With HEARTBEATs stalled but ticks flowing, `fresh`
is `True`, `222 not in resting` is `True`, and `:805` deletes the row of an
order that is still resting at the broker — the CRITICAL-1 outcome, reached
through the guard that was added to prevent it. Nothing can re-register a swept
PENDING row (`state_manager.py:233`), so it fills into the release untracked and
uncounted by the portfolio cap.

**Honest bounding of the likelihood.** This needs HEARTBEAT-specific loss ≥60 s
while other message types keep arriving. I checked the two easier doors and both
are shut: `_wait_for_bridge_connection` is an unbounded `while True`
(documented at `:360-364`), so the loop is never reached without an EA; and
under a *total* EA death no new PENDING rows can be registered, so the frozen
snapshot still contains every live ticket. In the current EA, TICK and HEARTBEAT
are emitted from the same `OnTimer` (`Titan_Gateway.mq5:50-101`), so the
divergence needs a HEARTBEAT-specific drop — e.g. `SendHeartbeat`'s
`socket_push.Send` return is unchecked (`:239`), and HEARTBEAT is by far the
largest message (full `pos` + `orders` arrays). That is why I rate this MINOR
rather than MAJOR. It is still a real, reproducible hole in a safety guard, and
the fix is trivial.

**Remediation.** Stamp a dedicated timestamp in the HEARTBEAT branch beside
`current_pending_orders` (`:1526-1527`) — e.g. `self.last_book_snapshot_at =
datetime.now()` — and have `_news_feed_is_fresh` read *that*, defaulting to
`False` when it has never been set. That also removes the `_reboot_terminal`
fabrication and makes the boot case (`__init__:161` seeds
`last_heartbeat_time = datetime.now()` before any EA contact) correct by
construction rather than by the happy accident that `attempts` is still 0.

**Test gap.** `test_confirmation_is_not_believed_on_a_stale_feed`
(`test_controller_news_gate.py:413-423`) sets `last_heartbeat_time` directly, so
it passes identically against either source and cannot see this. The regression
test is: deliver a `TICK` through `_process_incoming_data`, then assert the
sweep still refuses to confirm.

### R2·4 · Observations (no remediation required — recorded so they are not re-discovered)

1. **Cleared-window orphan rows become phantom trade-history entries.** When a
   window clears with a cancel still unproven, `:816-823` drops the attempt
   counter and leaves the row for the Sync Guard, which is deliberate and
   documented. But the Sync Guard's handler is `archive_trade(tid, 0.0)`
   (`:652`), which inserts a **0-P&L row into `trade_history`**
   (`state_manager.py:251-264`) and Telegrams "Closed externally" rather than a
   news-pull confirmation. A cancelled order that never filled therefore shows
   up as a break-even trade in `get_day_stats`. Narrow, and the same is already
   true of any hand-cancelled pending, so it is not this session's defect — but
   this sweep is a new route into it.
2. **Asymmetric dict hygiene between the two sweeps.** The news sweep purges
   `_news_cancel_sent` against `live_rows` (`:850-855`); the breaker sweep has
   no equivalent for `_dd_breaker_cancel_sent`. When the news sweep confirms and
   deletes a row, the breaker's dict keeps a stale key forever. Pre-existing
   (RS022 scope) and harmless, but the asymmetry is now visible in one file.
3. **Both sweeps can chase the same ticket.** A DD trip plus a news block sends
   two independent CANCEL streams (breaker every ~5 s heartbeat, news on the
   60 s tick) and two independent operator notices. Duplicate CANCELs are a
   no-op at the EA; the cost is Telegram noise on the worst day of the month.
4. **`is_globally_blocked` is consulted twice per symbol** — once directly at
   `:691`, again inside `check_symbol` (`manager.py:108`). Both are cheap
   `store.age()` walks; noted only so it is not mistaken for a bug later.
5. **Line endings.** The added lines are CRLF, matching the file (2120 CRLF, 0
   bare LF at HEAD). No mixed-ending damage.
6. **Blast radius is smaller than round 1 assumed.** `max_cache_age_hours: 48`
   (`config/config.yaml:261`) means the documented DNS/news-feed flap — which
   self-heals on the hourly retry — cannot drive the calendar stale and pull the
   book. The whole-book path is genuinely limited to a ≥48 h feed outage or a
   `check_symbol` code fault, and in both cases pulling the book is the intended
