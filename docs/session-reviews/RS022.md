## Findings

### MAJOR-1 — the sweep deletes the DB row whether or not the CANCEL landed, and the latch guarantees it is never retried

`src/core/system_controller.py:824-830`

```python
for o in (self.state_manager.get_pending_orders() or []):
    ticket = o['ticket_id']
    await self.bridge.send_command("CANCEL", {"ticket": ticket})   # return value discarded
    self.state_manager.delete_order(ticket)
```

Three facts make this a hole rather than a style nit:

1. `ZMQBridge.send_command` (`src/execution/bridge_zmq.py:74-81`) returns `False` on any send
   failure and swallows the exception; the caller ignores it. Beyond that, `CANCEL` is
   fire-and-forget on PUSH, so an EA-side *rejection* (e.g. retcode 10018, market closed) is
   invisible to Python by design — `CLAUDE.md` says the project's answer to this is that
   "management outcomes are verified from HEARTBEAT state instead". This sweep performs no such
   verification, and the heartbeat that would provide it (`msg['orders']`, already in hand at the
   call site) is not consulted.
2. The row cannot come back. `state_manager.py:233-234` states it outright: *"nothing can
   re-register a swept PENDING row, because the heartbeat's `orders` entries carry no SL"*.
3. `self._dd_breaker_tripped = True` is set at `:818`, **before** the loop, so the sweep runs
   exactly once per trip. There is no second attempt.

Failure scenario (reproduced): a Titan LIMIT is resting when the breaker trips; the CANCEL does
not take. Result — the order is still live at the broker, its DB row is gone forever, and no
retry ever occurs. I drove this through the real code path with a bridge whose `send_command`
returns `False` exactly as `ZMQBridge` does on error:

```
B: sent: [('CANCEL', {'ticket': 777})] | db rows left: [] | deleted: [777]
B: retries on later heartbeats: 0
```

Consequences, in order of severity:

- The session's own second objective is silently unmet: the order can still fill after the trip,
  adding exposure on a max-loss day — the exact defect the task exists to close.
- It is now *worse* than before the change for the portfolio cap. `_execute_signal:670` sources
  resting risk from `state_manager.get_pending_orders()`; with the row deleted, the live order
  becomes exactly the "manually placed pending with no DB row" that `CLAUDE.md` documents as the
  cap's known blind spot. Before this change the row existed and was counted.
- If it later fills, `exists(tid)` is false, so the heartbeat adoption path
  (`:1037-1046`) re-registers it as strategy `"Adopted"` / `"MARKET"`, losing the strategy
  attribution, the grade and the journal linkage.

Minimal remediation: gate `delete_order` on the `send_command` return value, and stop latching the
*sweep* — keep the alert one-shot but re-attempt the cancel on subsequent tripped heartbeats until
the ticket is absent from the heartbeat's `orders` list. That is the codebase's own
verify-from-HEARTBEAT convention and it also fixes MINOR-4.

### MAJOR-2 — no hysteresis: equity oscillating across the trip line re-alerts and re-sweeps on every crossing

`src/core/system_controller.py:812-818`

The latch arms on `check_can_trade() == True` and fires on `False`, both evaluated against the
*same* threshold (`risk_manager.py:253-254`, `pnl_pct > -max_dd`). `current_equity` is
mark-to-market equity including floating P&L, refreshed every heartbeat, and the EA heartbeats
every 5s (`Titan_Gateway.mq5:98`). A losing open position sitting near −3.00% therefore flips the
verdict repeatedly, and each crossing is a fresh "trip": a full Telegram plus a `RISK:BREAKER`
log line.

Confirmed against the **real** `RiskManager` (anchor 10 000; equity oscillating by ±$1–2 either
side of the −3% line):

```
eq=9699.0 can_trade=False alerts=1
eq=9701.0 can_trade=True  alerts=1
eq=9699.0 can_trade=False alerts=2
eq=9701.0 can_trade=True  alerts=2
eq=9698.0 can_trade=False alerts=3
eq=9702.0 can_trade=True  alerts=3
```

Three round-trips → three alerts; at 5s heartbeats that is up to ~12 Telegrams/minute during
precisely the most stressful minutes of a trading day. `Telemetry._async_send_retry`
(`src/ops/telemetry.py:89-101`) fire-and-forgets with 3 retries, so a Telegram 429 from the storm
can also drop *other* alerts queued at the same moment.

The docstring's justification for choosing a boolean over a throttle — *"a max-loss day is a
single discrete event, not an ongoing condition to re-nag about"* (`:806-807`) — is the part that
is wrong: with an equity-based breaker and floating P&L, a trip is not discrete. The sibling
alarm in the same file, `_alert_uncomputable_book` (`:758-785`), already solves this with
`UNCOMPUTABLE_ALERT_INTERVAL_S`; this one should either reuse that throttle or require the
re-arm to clear by a margin (e.g. back above `−(max_dd − 0.25)%`, or N consecutive healthy
heartbeats).

### MINOR-3 — the operator-facing text states the wrong recovery condition

`src/core/system_controller.py:646-647` (skip log) and `:803` (docstring) say the halt lasts
*"until equity recovers **above the anchor**"*. It does not: `check_can_trade` clears as soon as
`pnl_pct > -max_dd`, i.e. equity back above `anchor × (1 − max_dd/100)` — the same line it tripped
on. The message overstates the recovery bar by the full 3%, and the inaccuracy is what conceals
MAJOR-2: the text describes hysteresis the code does not have. (The Telegram body at `:844-848` is
vaguer — "or until equity recovers" — and is not wrong, only unspecific.)

### MINOR-4 — the sweep runs before the heartbeat's own `pos`/`orders` are applied

`_check_dd_breaker()` is awaited at `:1028`, while `self.current_open_positions` /
`current_pending_orders` are assigned from the same message at `:1030-1031`, and the
`PENDING→ACTIVE` flip happens later still in the adoption loop (`:1037-1053`). So on the heartbeat
where a LIMIT fills *and* the breaker trips, `get_pending_orders()` still returns the filled
ticket; the sweep sends a doomed CANCEL and deletes the row of a now-live position, which the
loop below then re-adopts as `"Adopted"`. Reading `msg['orders']` before sweeping (which MAJOR-1
needs anyway) removes this ordering hazard.

### MINOR-5 — `_check_dd_breaker`'s guard and the `__init__` latch are uncovered

The commit message justifies two `getattr(..., 'check_can_trade', None)` guards. The one in
`_execute_signal` (`:641`) *is* exercised, incidentally, by the pre-existing
`test_execute_signal_sizing_log` whose `ZeroLotRisk` fixture has no `check_can_trade` — good, and
it confirms the guard was necessary. The one in `_check_dd_breaker` (`:810-812`) is not: every
fixture in the new file (`ScriptedRisk`, test file:111-112) implements the method, so the
early-return is never taken. Likewise `_controller()` (test file:141) sets
`c._dd_breaker_tripped = False` by hand, so the initialisation at `system_controller.py:186` is
uncovered — deleting that line would not turn anything red (the code only survives it because of
the defensive `getattr(self, '_dd_breaker_tripped', False)` at `:816`). Two three-line tests
close both.

### MINOR-6 — divergence from the "`_process_incoming_data` must stay pure data-routing" rule

`system_controller.py:549-552` records this as a deliberate, recently-learned convention
("Kept out of the HEARTBEAT branch on purpose: this is periodic bookkeeping like the Sync Guard
and ghost cleanup above, and `_process_incoming_data` must stay pure data-routing"). The new code
puts a DB write loop, bridge sends and a Telegram inside that branch. The *detection* half is
legitimately equity-event-driven and belongs there; the sweep half is bookkeeping of exactly the
kind the comment excludes, and `_cleanup_ghost_orders` (its structural twin) lives in the main
loop. Either move the sweep or amend the comment so the next reader is not misled.

## Adversarial traces that came back clean

- **Anchor source.** `_check_dd_breaker`'s `day_start_equity → starting_balance` fallback
  (`:831-833`) matches `check_can_trade` exactly (`risk_manager.py:249`), so the reported % can
  never disagree with the verdict. (Note the GUI's `_risk_block` uses `day_start_equity` only —
  the new code picked the right one.)
- **Warm-up / boot.** `check_can_trade` returns `True` when the anchor is 0, so no phantom trip
  before the first heartbeat; `_check_dd_breaker` is only reached under `eq > 0` (`:1023`).
- **Day rollover.** `roll_daily_anchor` (`risk_manager.py:497-522`) re-anchors to live equity →
  `check_can_trade` True → latch re-armed (`:814`). A trip on the following day alerts again. Covered by
  `test_recovery_rearms_so_a_second_trip_alerts_again`.
- **Restart while tripped.** `_dd_breaker_tripped` is in-memory only, so a restart re-announces
  the trip and re-sweeps — the right default, and it partially bounds MAJOR-1.
- **Reconciliation.** `reconcile_state` (`state_manager.py:226-246`) only *removes* DB rows; it
  never adds, so the sweep cannot fight the Sync Guard.
- **PAUSED.** `_check_dd_breaker` runs on the heartbeat regardless of `BotState`, so a paused bot
  still pulls its pendings on a trip. Correct, and consistent with S019's direction.
- **Exception safety.** A raise inside the sweep propagates to the main loop's fatal handler
  (`:563-567`), which Telegrams `FATAL SYSTEM CRASH` and re-raises. Loud, not silent — and
  `send_command` swallows its own exceptions anyway, which is what produces MAJOR-1 instead.
- **Message size / Markdown.** At most a handful of tickets per trip; ticket and symbol are the
  only interpolated values and are backticked/plain. No 4096-char or parse-mode hazard.
- **Scope.** No out-of-scope file touched; `_execute_signal`'s non-breaker path is byte-identical
  in behaviour (proved by `test_untripped_breaker_keeps_todays_specs_missing_message`, the one
  test that also passes on main).

## Three-axis read

- **Does it work?** The detection and labelling halves do, and are well tested. The cancellation
  half works only when the wire and the EA cooperate, with no verification and no retry (MAJOR-1).
- **Is it safe?** No new risk-taking path; the change only removes exposure. The two real hazards
  are an alert storm at the worst moment (MAJOR-2) and a permanently untracked live order that
  blinds the portfolio cap (MAJOR-1).
- **Is it worth it?** Yes — small, well-anchored, closes a genuine audit finding (2026-08-07 D9)
  and subsumes the alerting half of `risk-14-daily-limit-trip-is`. The findings are all
  small-diff remediations, not a redesign.
