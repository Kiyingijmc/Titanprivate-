## Findings

### MAJOR-1 — a CANCEL the *EA* refuses is announced exactly once, then never again — while the trip Telegram has already told the operator the order is being pulled

`src/core/system_controller.py:889-897` (re-send + one-shot WARN), `:954-977` (the alert body).

The remediation correctly separated the two failure modes and correctly kept the DB row. But the
escalation is asymmetric with how long the failure can last:

```python
sent[ticket] = attempts + 1
if attempts == 0:
    requested.append(label)          # goes into the trip Telegram: "Cancelling resting orders: #111"
elif attempts == 1:
    # One WARN per stuck ticket, not one per 5s heartbeat.
    self.logger.log_event("WARN", "BREAKER", f"CANCEL for #{ticket} did not take …")
```

After `attempts == 1` there is no further log, no Telegram, and no bound — the CANCEL is re-pushed
every heartbeat forever. Driven through the real code path with the shipped fixtures, 100 tripped
heartbeats (≈8 minutes of live time) with the order still resting at the broker:

```
=== PROBE 3: a permanently-refused CANCEL over 100 tripped heartbeats ===
  CANCELs sent: 100 | WARN lines: 1 | telegrams: 1
  order still resting at broker the whole time; row kept: [111]
```

Why this matters rather than being a style nit:

1. `CANCEL` is fire-and-forget on PUSH, so an EA-side rejection is invisible to Python by design —
   `CLAUDE.md` and the project's own operating notes are explicit that a refused command still
   "succeeds" from Python's side and the only proof is the MT5 Experts log (retcode 10018 market
   closed, **10027 AutoTrading disabled**). `send_command` returned `True`; only the heartbeat can
   contradict it, and the code correctly notices — it just never says so again.
2. The AutoTrading-disabled case is the sharp one: the EA keeps publishing `TICK`/`HEARTBEAT` from
   its timer, so the sweep keeps running and keeps being refused — **but broker-side pending orders
   fill regardless of AutoTrading state**. The order the breaker exists to remove can fill on a
   max-loss day, which is the exact defect this session was opened to close.
3. The operator's only notice is a Telegram (`:971-977`) that asserts the opposite:
   `"Cancelling resting orders: `#111` EURUSD"`. That claim is never corrected. The single WARN
   lands ~10s after the trip and is then buried by everything else the log writes over the
   following hours.

Minimal remediation, in the codebase's own idiom: track the first-attempt timestamp per stuck
ticket and, once a ticket has gone unconfirmed for longer than a threshold, Telegram the operator
naming it — throttled exactly the way `_alert_uncomputable_book` /
`UNCOMPUTABLE_ALERT_INTERVAL_S` (`:88`, `:785-810`) already does for the sibling "everything is
blocked and you can't see why" alarm. That is the same precedent the class docstring cites, and it
is a ~10-line change with an obvious test (N tripped heartbeats with a refusing broker → a second
Telegram naming the ticket).

### MINOR-2 — the un-sent branch logs a WARN on *every* heartbeat, while its sibling three lines below is deliberately throttled to one

`src/core/system_controller.py:882-888` vs `:892-897`.

The refused branch carries the comment *"One WARN per stuck ticket, not one per 5s heartbeat."*
The un-sent branch (`send_command(...) is False`) has no such throttle, and it never increments
`sent[ticket]`, so it re-logs unconditionally:

```
=== PROBE 7: wire down for 100 tripped heartbeats (send_command -> False) ===
  WARN lines emitted: 100 (one per heartbeat = 720/hour)
  sample: CANCEL for #111 failed to send; DB row kept, retrying on the next heartbeat while the brea…
```

720 WARN lines/hour into `system.log` during precisely the window an operator is reading it, and it
buries the one line that matters (the trip itself). The comment three lines below shows this was
not an intended asymmetry. A per-ticket "already warned" flag (or reusing the same `sent` map with
a sentinel) fixes both branches with one mechanism.

### MINOR-3 — the *confirmed* pull is completely silent

`src/core/system_controller.py:877-881`.

```python
if attempts and ticket not in resting:
    self.state_manager.delete_order(ticket)
    sent.pop(ticket, None)
    continue
```

No log line, no Telegram. Probed:

```
=== PROBE 2 ===
  deleted: [111] | rows left: []
  log lines about the delete: []
  ALL log lines: ['BREAKER:DAILY DRAWDOWN BREAKER TRIPPED: equity $9,600.00 vs anchor $…']
```

Two consequences:

- The operator is told "Cancelling …" and never told it completed. In a session whose entire
  purpose is that this subsystem stop being observable only by inference, the success path is the
  one thing left un-observable. Compare the sibling: `_perform_reconciliation` Telegrams
  `"Sync Guard: Resolved Ticket #N"` for **every** row it removes (`:607-609`), and
  `_cleanup_ghost_orders` Telegrams `"Auto-Clean: Expired …"` for every one it cancels (`:1198-1201`).
  This sweep is the only DB-row remover in the file that says nothing.
- The confirmation rests on a single heartbeat snapshot with no grace period, whereas the Sync
  Guard — using the *same* corroboration source — deliberately applies `grace_s=120`
  (`state_manager.py:226-237`) because "nothing can re-register a swept PENDING row". A heartbeat
  that under-reports `orders` for one cycle therefore deletes the row silently. That risk is small
  (and it is the project's own convention), but with no log line there is no way to reconstruct
  afterwards that the sweep was the thing that removed the row.

A single `log_event("RISK", "BREAKER", f"CANCEL for #{ticket} confirmed …")` closes it.

### MINOR-4 — the halt is Telegrammed; the resume is not

`src/core/system_controller.py:934-946` vs `:971-977`.

The trip sends a Telegram stating *"No new entries for the rest of the day (or until equity
recovers above the day-loss line)"*. The re-arm writes a `RISK:BREAKER … RE-ARMED` **log line
only**:

```
=== PROBE 5: re-arm is LOG-only (no Telegram) ===
  telegrams before re-arm: 1 after: 1
  re-arm log: [('RISK', 'BREAKER', 'Daily drawdown breaker RE-ARMED: equity $9,750.00 …')]
```

So a standing operator-facing claim ("no new entries") silently becomes false, and the operator has
no way to know the bot resumed taking risk short of tailing the log. This is a change-introduced
gap: before this session there was no such claim to go stale. One `telemetry.send_message` on the
re-arm branch, symmetric with the trip.

## Adversarial traces that came back clean

- **Hysteresis maths.** `margin = min(DD_BREAKER_REARM_MARGIN_PCT, max_dd * 0.5)` (`:834`) — a
  small or zero `max_dd` cannot invert the band or disable the breaker; `max_dd <= 0` returns
  `True` so the breaker's own verdict remains the only gate.
- **Anchor source.** `_dd_breaker_pnl` (`:814-823`) reproduces `check_can_trade`'s
  `day_start_equity → starting_balance` fallback exactly (`risk_manager.py:249`), so the % quoted
  in the alert can never disagree with the verdict that produced it.
- **Day rollover.** `_maybe_roll_trading_day` → `roll_daily_anchor` (`:337`, `risk_manager.py:497`)
  re-anchors to live equity → `check_can_trade` True *and* `pnl_pct ≈ 0` clears the band → latch
  re-arms and the cancel map is dropped (`:936-939`). A trip on the new day alerts again.
- **Sync Guard cannot fight the sweep.** `current_pending_orders` is only refreshed on HEARTBEAT,
  and the sweep runs at the end of that same branch — so any heartbeat in which the ticket
  disappears is one in which the sweep has already deleted the row. `_perform_reconciliation`
  (60s cadence) can never observe the gap, so no spurious "Closed externally" Telegram. Verified by
  reading the ordering, not assumed.
- **`_cleanup_ghost_orders` overlap.** Both may delete the same row; `delete_order` is idempotent
  and swallows, so the worst case is one redundant "Auto-Clean" Telegram.
- **Adoption path.** The `filled` guard (`:874-875`) plus running after `backfill_position_state`
  means a LIMIT that fills on the trip heartbeat is never cancelled and never has its row deleted —
  so it cannot be re-adopted as `"Adopted"`/`"MARKET"` with its strategy, grade and journal linkage
  lost. Directly tested.
- **Latch isolation.** Class-level defaults with instance shadowing (`:104-105`, `:866-868`); no
  mutable class attribute is ever mutated in place. `test_instance_latch_does_not_leak_between_controllers`
  pins it.
- **Restart while tripped.** In-memory latch → a restart re-announces and re-sweeps. Correct
  default, and it bounds MAJOR-1.
- **Boot / warm-up.** `check_can_trade` returns `True` when the anchor is 0, and `_check_dd_breaker`
  is reached only under `eq > 0` (`:1188`) — no phantom trip before the first heartbeat.
- **PAUSED / non-ACTIVE.** The HEARTBEAT branch has no state gate, so a paused bot still pulls its
  pendings on a trip. Correct, and consistent with S019's direction.
- **Cost while tripped.** One `SELECT … WHERE status='PENDING'` per heartbeat (probe: 50 calls over
  50 heartbeats) on a WAL connection — negligible.
- **Message safety.** Only ticket and symbol are interpolated, both backticked/plain; a handful of
  tickets per trip, so no 4096-char or parse-mode hazard. `**bold**` with `parse_mode="Markdown"`
  matches every other message in the file (pre-existing convention, not introduced here).
- **Exception safety.** The real `StateManager.get_pending_orders`/`delete_order` and
  `ZMQBridge.send_command` all swallow their own exceptions, so the sweep is practically
  non-raising. (If it *did* raise it would pre-empt the trip alert, since the sweep runs first —
  but the main loop's fatal handler Telegrams `FATAL SYSTEM CRASH`, so the failure is still loud.
  Noted, not raised: the path is unreachable with the real collaborators.)
- **Scope.** No out-of-scope file touched; no test weakened; `_execute_signal`'s non-breaker path is
  behaviourally identical, pinned by `test_untripped_breaker_keeps_todays_specs_missing_message`
  (the one test that also passes on `main`).

Two things I checked and am **not** raising as findings, recorded so the next reader need not
re-derive them:

- `send_command(...) is False` (`:882`) is an identity check; a bridge returning `None` would be
  read as success (probed). `ZMQBridge.send_command` (`bridge_zmq.py:74-81`) returns only `True`
  or `False`, so this is correct today — a fragility, not a defect.
- Equity oscillating across the **re-arm** band (a 0.25pp round trip) still produces one Telegram
  per round trip (probe: 6 round trips → 6 alerts). Each of those is a genuine re-trip after a
  genuine recovery, and this is exactly the remedy round 1 prescribed; ~12/minute has become
  ~1 per real 0.25% swing. Acceptable as shipped.

## Three-axis read

- **Does it work?** Yes. Detection, labelling, one-shot alerting, hysteresis and the verify-then-
  forget sweep all work and are pinned by tests that provably fail on both `main` and the
  pre-remediation commit. The one gap is escalation when the *broker* refuses the cancel (MAJOR-1).
- **Is it safe?** No new risk-taking path; the change only removes exposure and adds no bridge
  command, timer or schema. The residual hazard is a refused cancel leaving a live order on a
  max-loss day with the operator believing otherwise.
- **Is it worth it?** Yes. Small, well-anchored, closes audit-2026-08-07 D9 and subsumes the
  alerting half of `risk-14-daily-limit-trip-is`. The findings below are all small-diff
  observability work in the direction the session already goes — none is a redesign.
