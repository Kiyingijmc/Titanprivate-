## Task and Definition of Done

Backlog row (`_BACKLOG.md:21`, source `review-carry`, from RS004 MINOR):
hash-anchor the archive↔live seam in `event_log.verify_chain` — `_write_parquet`
stores `chain_last_row_hash` in Parquet metadata but nothing ever reads it, so
after an archive the retained SQLite chain is anchored on a *seq* watermark
only; `verify_chain()` cannot prove the retained chain continues the archived
one.

RS004's finding (`docs/session-reviews/RS004.md:140-159`) specifically calls
out two independent holes on the same seam:
1. `verify_chain` (including the `from_seq=N` parameter whose intended caller
   is M0-4's `verify_and_replay`) accepts the first retained row's `prev_hash`
   against nothing when that row immediately follows an archive boundary.
2. `_write_parquet` writes `chain_last_row_hash` into Parquet schema metadata
   but never reads it back, so a foreign row extending an existing archive
   file at a *new* seq (no seq/row_hash collision) is accepted uncontested.

## What the diff does

`tradebot/core/event_log.py`:
- Adds `_META_ARCHIVED_THROUGH_HASH = "archived_through_row_hash"` and
  persists it in the same `BEGIN IMMEDIATE` transaction as
  `_META_ARCHIVED_THROUGH` inside `archive_before` (`:846-847`), so the two
  watermarks can never desync.
- `verify_chain` (`:587-603`): when the first row walked lands exactly at
  `archived_through + 1`, it now requires `archived_through_row_hash` to be
  present and to equal that row's `prev_hash`, raising `RecoveryRequired`
  otherwise. Because `expected_first = max(from_seq, archived_through + 1)`
  (`:576`, unchanged), this also covers the `verify_chain(from_seq=N)` call
  shape RS004 called out as the real M0-4 caller — when `from_seq` lands
  exactly on the archive boundary, the same check fires; when `from_seq` is
  later (a live-only replay), the check correctly does not fire, since no
  cross-half claim is being made in that case.
- `_write_parquet` (`:1149-1195`): reads back `chain_last_row_hash` from the
  existing file's schema metadata before the dedup pass; after dedup, any row
  genuinely new to the file must chain (`prev_hash`) from that stored tail, or
  the write is refused with `RecoveryRequired`. This is ordered after the
  existing seq/row_hash-collision dedup, so a genuine retry (identical rows
  re-offered) is unaffected — only rows at new seqs with a wrong `prev_hash`
  are caught, which is exactly the gap RS004 identified as previously
  invisible to the seq/row_hash check.

`tests/unit/test_tradebot_event_log.py` adds four tests, each with teeth
verified by construction (they tamper/delete/forge exactly the field the new
check exists to catch) rather than merely re-asserting the happy path:
- `test_archive_persists_the_archived_through_row_hash_in_log_meta` — the new
  meta key is actually written and matches the archived tail's `row_hash`.
- `test_verify_chain_catches_a_tampered_archived_through_row_hash` — a
  post-archive log verifies clean, then tampering the stored anchor to
  `GENESIS_PREV_HASH` (a plausible-looking but wrong value, not a blank/None)
  makes `verify_chain()` raise.
- `test_verify_chain_requires_the_archived_through_row_hash_when_archived` —
  a *missing* anchor (simulating a pre-fix log_meta row) is treated as exactly
  as unproven as a wrong one, not silently trusted.
- `test_write_parquet_refuses_new_rows_that_do_not_chain_from_the_stored_tail`
  — a foreign row at a genuinely new seq (so the seq/row_hash dedup does not
  see it) is refused by the new tail-continuity check, calling `_write_parquet`
  directly.
