Confirmed against the pre-image (`git show HEAD~1:src/arbiter/arbiter.py`): `_bar_index`
was a single `int` advanced on every distinct `bar_key`, and `bar_key` is just the bar
timestamp (`system_controller.py:679`, `own_token`), carrying no timeframe. I reproduced

```

per-tf replay approved (must be False):     False      a 12-bar H1 thesis in one hour
```

Premise stands; the fix closes it.

## What the diff does

`src/arbiter/arbiter.py`:
- `_bar_index` / `_last_bar_key` become `timeframe -> …` dicts (`:88-91`).
- `_advance_bar(bar_key, timeframe)` (`:154-167`) advances **only** the arriving
  timeframe's counter and purges **only** entries stored under that timeframe
  (`tf == timeframe and current - idx >= ttl`, `:162-165`). The `_UNSET` sentinel
  keeps a first-ever `bar_key=""` from being mistaken for "same bar".
- `_thesis_memory[thesis]` becomes `(timeframe, index)` (`:188`), and
  `_apply_thesis_dedup` ages a thesis against `self._bar_index[seen_tf]` — the counter
  of the timeframe it was **seen** on, not the one resolving (`:179-181`).
- `resolve()` gains `timeframe=""` (`:127`); the default puts every legacy caller in one
  shared bucket, which is exactly the old behaviour.
- Module docstring rewritten to match (`:37-67`), including an honest "Accepted edge"
  paragraph about arrival-driven purging.

`src/core/system_controller.py:757`: the single live call site now passes `timeframe=tf`.

Rules 2–5 (dedup / opposition / symbol cap / total cap), `GRADE_RANK`, `priority`,
`Intent`, and the `stats()` shape are untouched — I diffed them line by line. No clock,
no randomness introduced; determinism invariant holds. `_bar_index` has no reader
outside `arbiter.py` (grepped `src/`, `scripts/`, `frontend/`), and `stats()` is
unchanged, so the GUI/telemetry surfaces are unaffected.

Blast-radius check on the two non-live drivers: `src/research/kernel_replay.py:144`
drives `_run_strategies(symbol, win, "H1")` — H1 only, so it lands in a single bucket
and is isomorphic to the old counter. Frozen-parity is therefore preserved by
construction, and `tests.unit.test_signal_parity` passes.

## Findings

### MINOR-1 (actionable) — the two invariants that *are* the fix are unpinned; a mutant passes the whole suite

`tests/unit/test_arbiter.py:212-341` adds seven tests, and they do have teeth for the
headline scenario (I confirmed a global-purge mutant — dropping `tf == timeframe` at
`arbiter.py:164` — is caught by `test_thesis_memory_is_bounded_per_timeframe`). But the
two subtlest lines in the diff are asserted by nothing. I verified this by mutation:
each mutant below is a *drop-in subclass* of the shipped `Arbiter` swapped into the
committed test module, running the committed suite unmodified.

```
M1_AgeAgainstResolvingTf     survives committed suite: True
M2_GlobalPurge               survives committed suite: False   <- correctly caught
M3_GlobalLastBarKey          survives committed suite: True
```

**M3 — per-timeframe `_last_bar_key` (`arbiter.py:157,161`) is unpinned, and this is the
realistic one.** Every committed test uses disjoint `bar_key` strings per timeframe
(`"h1"/"h2"` vs `"m5-0"…`), so nothing exercises the case the live loop hits *every
hour*: at 10:00 the M5 bar and the H1 bar both open at 10:00, and `own_token =
str(tf_df.iloc[-1]['time'])` (`system_controller.py:679`) yields the **identical string**
for both. A refactor that collapses `_last_bar_key` back to one scalar — a very
plausible "this dict looks redundant next to `_bar_index`" simplification — passes the
whole suite and then does this on the live path:

```
--- M3: the hourly H1/M5 token collision (both bars open at 10:00) ---
  Arbiter  M5 resolve on the colliding token -> ok, approved=True
  M3       M5 resolve on the colliding token -> KeyError: 'M5'
```

An unguarded `KeyError` inside `_run_strategies`, once an hour, on the M5 path. The
shipped code is correct here; the regression guard is missing.

**M1 — the `seen_tf` indirection (`arbiter.py:179-180`) is unpinned.** In every committed
test the thesis is stored and looked up on the same timeframe, so `self._bar_index[seen_tf]`
and `self._bar_index[timeframe]` are indistinguishable. Replacing the former with the
latter — i.e. deleting the diff's stated core rule, "a thesis is aged against the counter
of the timeframe it was SEEN on" — is green:

```
--- M1: H1-seen thesis replayed on M5 after 30 M5 bars ---
  Arbiter  approved=False
  M1       approved=True
```

(The cross-timeframe *collision* itself is hard to reach in practice, since
`effective_thesis()` is `symbol:direction:price!r:sl!r` (`intent.py:30-31`) and would need
byte-identical floats from two timeframes — but that is an argument about likelihood, not
a reason to leave the branch unasserted, and it evaporates the moment a strategy sets an
explicit `thesis_id`.)

**Bearing on the commit message.** `6934181` states the tests lock "symmetric M5-vs-H1
aging". They lock symmetric *counter isolation*; they do not lock either rule above. The
claim overstates the coverage by exactly the two lines a future editor is most likely to
touch. This project's own standing lesson (RS004: a session passed verify carrying a
CONFIRMED bug the suite did not see) is that a green suite is not the proof — so this is
worth one remediation pass, not a shrug.

*Suggested remediation (cheap — three asserts, no production change):*
1. A test that resolves H1 and M5 on the **same** `bar_key` string in one cycle and
   asserts both counters advanced (kills M3).
2. A test that seeds a thesis on H1, advances ≥ TTL M5 bars, replays the same thesis
   **on M5**, and asserts it is still blocked (kills M1).
3. A controller-seam assertion that `resolve()` receives `timeframe=tf` — see MINOR-2.

### MINOR-2 (actionable) — the controller wiring is unpinned; deleting the fix leaves the suite green

`system_controller.py:757` is the one line that makes the fix reach production. Every
controller-driven test is H1-only — `tests/unit/test_bias_exemption.py:31` (`timeframe =
"H1"`), `test_signal_parity.py` via `kernel_replay.py:144` (`"H1"`) — and for an H1-only
caller the `""` bucket and the `"H1"` bucket are isomorphic. So reverting
`arb.resolve(open_positions, bar_key=own_token, timeframe=tf)` to
`arb.resolve(open_positions, bar_key=own_token)` restores the exact defect this session
exists to fix, and the full suite still passes. Nothing detects the regression until an
M5 strategy is live — which is precisely the moment Advisory C says the fix must already
be in place. One assertion on a stubbed arbiter (record the kwargs `_run_strategies`
passes for `tf="M5"` and `tf="H1"`) closes it.

## Non-blocking observations (no action required)

- **A timeframe that goes quiet freezes its theses, it does not just leak memory.** The
  docstring's "Accepted edge" (`arbiter.py:60-63`) frames arrival-driven purging as a
  *memory* consideration. The operational consequence is stronger: a thesis stored under
  a timeframe that stops resolving stays **permanently replay-blocked**, not merely
  resident. Measured: a thesis seen on M5 is still blocked after 500 H1 bars, entry
  retained as `{'T': ('M5', 0)}`. In the live loop both timeframes are driven off the
  same tick stream, so they go quiet together and this is effectively unreachable today;
  it becomes reachable if a strategy set is ever changed at runtime such that one
  timeframe stops resolving. Worth one clause in that paragraph if it is ever revisited —
  not worth a change now.
- **`config/config.yaml:63` (`thesis_ttl_bars: 12`) carries no comment**, and its meaning
  changed from "12 global counter ticks" to "12 bars of the thesis's own timeframe". No
  behavioural difference under the current H1-only arsenal; a one-line comment would pay
  for itself when an M5 plugin lands.
- **Pre-existing, unchanged by this diff:** `resolve()` is called once per *(symbol, tf)*
  (`system_controller.py:551-557`, `:664`), so a timeframe's counter advances once per
  *distinct bar timestamp seen across all symbols*, not strictly once per bar. Symbols
  whose last closed bar desyncs (missing bars, differing session hours) can over-advance
  a counter. The old global counter had the identical property; the per-timeframe split
  strictly reduces spurious advances (an H1 close no longer masks a same-token M5 close).
  Out of scope for this session — noting it so it is not mistaken for something this diff
  introduced.
- **Backlog slug is a misnomer** ("FeatureBus" vs the arbiter). Bookkeeping owned by the
  orchestrator; recorded here only so the next reader of `_BACKLOG.md:6` does not go
  looking in `src/features/`.

## Three-axis readiness

- **Does it work?** Yes. The defect is real and reproduced; the fix is correct on every
  path I probed, including the hourly H1/M5 token collision that the tests miss;
  `stats()`, rule order, determinism and frozen H1 signal parity are all preserved; the
  `timeframe=""` default makes the change genuinely inert for every pre-existing caller.
- **Is it safe?** Yes for today's H1-only arsenal — the live behaviour is provably
  unchanged (parity green, single bucket isomorphic). The risk is not in what shipped but
  in what is not fenced: two of the three lines that constitute the fix, plus the
  controller wiring, can each be reverted or "simplified" with a fully green suite, and
  one of those regressions is a per-hour `KeyError` in the tick loop.
- **Is it worth it?** Yes — Advisory C names this a required precondition for both the
  live flip and any M5 arsenal strategy, and this is the smallest change that satisfies
  it. Good judgement in keeping `Intent`, the rule pipeline, and `stats()` untouched.

The production change is sound and I would not ask for a line of it back. The findings
are entirely about test teeth: one pass adding three assertions (two in
`tests/unit/test_arbiter.py`, one on the controller seam) closes MINOR-1 and MINOR-2
without touching `src/`.
