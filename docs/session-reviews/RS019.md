## 2. Premise re-confirmed in the live tree

The defect the session claims was real, and it is the one recorded in the 2026-08-07
full-system audit ("PAUSED freezes in-trade management"):

- `BotState` has five members (`system_controller.py:51-52`); `PAUSED` is reached from two
  independent places — the operator (`set_system_pause`, `:1460-1464`, wired to Telegram
  `/pause` at `src/ops/telemetry.py:159-160` and to the GUI at `src/ops/web/commands.py:11-12`)
  and the stale-calendar auto-pause (`_check_news_status`, `:1182-1186`).
- `TradeManager.sync_positions` has exactly **one** caller in the whole tree
  (`system_controller.py:919`), inside the `TICK` branch. So before this commit, `PAUSED`
  really did mean *zero* in-trade management: no break-even, no partials, no runner trail,
  no time-exit, and no emergency kill-switch (`trade_manager.py:156-162`).
- Nothing else compensates. The 60s main-loop jobs that keep running while paused —
  `_perform_reconciliation` (`:572-586`) and `_cleanup_ghost_orders` (`:969-978`) — only
  reconcile DB rows and cancel *pending* orders; neither touches an open position's SL.

So a `/pause` (or a news-feed outage long enough to trip the stale-calendar guard —
a failure this project has actually seen, per the 08-04 DNS-flap note) previously abandoned
the open book. That is the same shape as the 08-03 stopless-GBPJPY incident. Premise good.

## 4. Is the fix complete, and is it complete *only* where it should be?

**Complete.** I enumerated every `self.state` read in the controller
(`grep -n 'BotState\.'`): `:95`, `:450`, `:455`, `:916`, `:925`, `:1182-1188`, `:1453`,
`:1462`, `:1497`. The only two that gate per-tick work are `:916` and `:925`. There is no
second place where management is frozen, so the one-line widening is the whole fix.

**Reaches the live path end-to-end, not just the `if`.** I checked the inputs management
needs are still fresh while paused:

- `current_open_positions` / `current_pending_orders` come from the `HEARTBEAT` branch
  (`:944-945`), which is ungated. ✅
- `live_prices` is set in the `TICK` prologue *above* both gates (`:905`). ✅
- `state_manager.backfill_position_state` (`:965-967`) is ungated, so `initial_entry` /
  `initial_tp` still get filled while paused — meaning the ratchet can even engage for the
  **first** time during a pause. That is the non-obvious half of this fix and it works.
- The main loop (`run()`, `:430-556`; its `while True` is `:483`) has no state gate at all,
  so ticks keep flowing while paused. ✅

**No new risk can be opened while paused.** Traced every reachable outbound command:
`_dispatch_mgmt_command` (`:766-814`) emits only `MODIFY`, `CLOSE_POS` and `CLOSE_POS`+volume.
`_execute_signal` (`:598`) has exactly two callers, both inside `_run_strategies` (`:1118`,
`:1152`), whose only caller is `:934` — behind the still-`ACTIVE`-only gate. `_run_strategies`
itself is reachable from nowhere else in `src/` except `src/research/kernel_replay.py:144`,
which builds its own controller and never calls `_process_incoming_data`. The comment's
claim at `:923-924` holds.

**Ordering.** The commit also swaps the order of the two halves (management now runs
*before* `process_tick`). Harmless: `sync_positions` reads only `live_prices` (set at `:905`)
and `current_open_positions` (set on `HEARTBEAT`), never the candle buffer, and
`_process_incoming_data` is awaited serially from the single main loop. No coroutine mutates
`market_data` during the `await`s in `_dispatch_mgmt_command`.

## 5. Adversarial pass on the safety envelope

Five things I went looking for, and what I actually found:

1. **Can a paused bot now take a discretionary, non-protective action?** One, and it is
   defensible. With `runner.enabled: true` (live in `config/config.yaml:107-108`), the
   `Ratchet L3` MODIFY sends `tp = 0.0` (`trade_manager.py:217-219`) — it *removes* the
   take-profit and hands the tail to the trail. That is variance-increasing. But the same
   command sets SL to the L2 price, i.e. a floor at ~61.8 % of the original range **in
   profit**, and the two cannot be separated — they are one `MODIFY`. The alternative
   (freezing) leaves the position with its original stop and no BE at all, which is strictly
   worse. Not a defect.
2. **Does `/pause` still mean "the bot sends nothing to the broker"?** No — that property is
   gone, deliberately. But the operator is not left guessing: every `Ratchet L1/L2/L3` and
   every `Risk Guard` close fires a Telegram through `notify_management` /
   `notify_partial` (`:802`, `:808`, `:814` → `src/ops/telemetry.py:73-78`). So management
   acting during a pause is visible in real time on the same channel the operator paused
   from. (`Runner Trail` MODIFYs are excluded from notification at `:786` — but that is
   pre-existing, identical in `ACTIVE`, and only ever tightens a stop already in profit.)
3. **Does the ratchet now chase a stale feed while paused?** It can, and the backlog already
   knows: `exec-07-a-frozen-price-feed` (`docs/sessions/_BACKLOG.md:44`) — "a frozen price
   feed with live heartbeats is completely undetected." This commit widens the window in
   which that undetected staleness has consequences from `ACTIVE` to `ACTIVE|PAUSED`. It does
   not create the hole, and the exposure while `ACTIVE` (which also *opens* trades on a
   stale feed) strictly dominates it. Recording it here, not charging it to this session.
4. **Is the `_readiness()` analogy in the comment accurate?** Yes — `:1453` gates on exactly
   `(ACTIVE, PAUSED)`, so the new grouping matches the one the health probe already uses.
   The comment is not overclaiming.
5. **Does any doc now contradict the code?** No, and it got *less* wrong.
   `docs/TRADE_MANAGEMENT.md:45` says in-trade management runs "on every tick" — which was
   false before this commit (it was `ACTIVE`-only) and is closer to true after it. No
   operator-facing string anywhere promises that pause halts management: the Telegram reply
   is `⏸️ System: PAUSED` (`telemetry.py:160`), the GUI button is labelled `Pause`
   (`frontend/src/components/Controls.tsx:108-109`), and `get_status_report` (`:1358-1361`)
   just prints the state name.

## 7. Findings

**None at CRITICAL, MAJOR or MINOR.**

Three observations, none of which a remediation pass needs to act on:

- **OBS-1 — `EMERGENCY` is still frozen, and the new comment (`:914-915`) states that as
  settled without arguing it.** The session's own rationale ("the only things standing
  between a live position and an unmanaged loss") applies verbatim there: `trigger_panic`
  (`:1496-1501`) fires `CLOSE_POS` fire-and-forget with no verification, and on this project
  EA rejects are invisible to Python — so a panic that fails to flatten (market closed,
  retcode 10018) leaves an open, permanently unmanaged book. The escape hatch exists but is
  undocumented and counter-intuitive: `set_system_pause(True)` (`:1460-1464`) sets `PAUSED`
  unconditionally, *including from `EMERGENCY`*, so `/pause` un-freezes management after a
  failed panic. This is pre-existing, out of S019's one-task scope, and belongs in the
  backlog — not in this diff.
- **OBS-2 — a paused bot still builds no candles**, so a long pause leaves a hole in the
  `CandleMaker` buffer and the first post-resume bar is stitched onto a stale predecessor
  (`src/core/candle_maker.py:126-140`). Unchanged by this commit — `process_tick` was
  `ACTIVE`-only before and after. Worth knowing that the new comment at `:923-924` frames it
  as the mechanism for suppressing entries, when in fact the `:925` gate on
  `_run_strategies` is what does that work; not building candles is a side effect with a
  cost, not the safeguard.
- **OBS-3 — test fidelity, cosmetic.** The fixture's `TICK` dict (`test_...py:96`) has no
  `t` key, which the real `MultiTimeframeStore.process_tick` requires
  (`candle_maker.py:109`). It only works because `RecordingMarketData` is a stand-in. That is
  the right stand-in for these assertions, but the test would not survive being re-pointed at
  the real buffer.
