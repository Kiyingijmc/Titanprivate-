## Priority 1 — is rejection a strict no-op?

Yes. Read at the source level, not just from the tests:

- Validation is a two-pass structure. Pass 1 builds a **local** `clean` dict;
  every failure path is `return self._reject_specs(...)`, which returns `None`
  and never touches `self.symbol_specs`. There is no write before the last line.
- The single store write is `self.symbol_specs[symbol] = clean` — a **whole-dict
  replacement** after every field has passed, so no half-write and no field-wise
  merge into an existing entry is possible.
- The jump guard reads `prior = self.symbol_specs.get(symbol)` — the accepted
  store — and there is no separate "last seen" state anywhere in the class. A
  rejected frame therefore cannot become the next baseline. M3 and M3b confirm
  the tests would catch a change to either property.
- `_reject_specs` is guarded by `if self.logger:`, so the backtester/replay path
  (which passes `logger=None`) cannot raise — covered by
  `NoLoggerIsSurvivable`.
- No coercion survives a rejection: the `except (TypeError, ValueError)` around
  `float(raw)` returns rather than substituting a default, which is the exact
  behaviour the old `except ValueError: pass` lacked.

**The `calculate_lot_size` fail-safe is preserved.** A symbol whose only update
was rejected never gets a `symbol_specs` entry, so `if not (spec and
spec['val'] > 0 and spec['ts'] > 0)` still returns `0.0` and logs
`No broker specs for {symbol}`. Verified directly by
`FailSafeIsPreserved.test_symbol_whose_only_update_was_rejected_still_sizes_to_zero`
and, by mutation, by M2/M4 (both of which break it the moment a bad value is let
into the store).

### The jump guard essentially cannot false-reject, because of the frame cadence

This is the fact that settles the question, and it is not in the spec or the
commit message. I traced the actual production cadence of spec updates:

- `update_symbol_specs` has exactly one production caller,
  `system_controller.py:613`, on `msg_type == 'HISTORY'`.
- `HISTORY` is emitted by the EA only in reply to `GET_HISTORY`
  (`Titan_Gateway.mq5:251-285`).
- `GET_HISTORY` has exactly two send sites, `system_controller.py:927` (M5) and
  `:930` (H1), both inside `_perform_warmup`.
- `_perform_warmup` is called from exactly one place, `system_controller.py:287`,
  **once per process, at boot**. There is no periodic re-request.

So on the legitimate path each symbol receives exactly **two** spec frames per
process lifetime, seconds apart, from the same broker snapshot. The first has no
`prior` and is checked by the envelopes alone; the second compares against
values that are identical or differ by a fraction of a percent. And
`symbol_specs` is a plain in-memory dict initialised empty in `__init__` with no
persistence (`data/specs.json` is written by `scripts/cache_specs.py` for the
HTTP-bridge path and is never loaded into it), so a genuine 4-digit→5-digit
regrade observed across a restart arrives as a *first* frame with no baseline and
is accepted.

**The tape confirms this cadence empirically.** Counting raw `SpecsUpdated`
records in `data/journal/events-20260731.jsonl`: 20 events across 12 symbols —
**exactly two for each of eight symbols, one each for the remaining four**
(US30, US100, GBPUSD, AUDUSD, whose second warmup reply landed outside the
bounded 20-iteration poll window). Never more than two. The multiple distinct
values visible for GBPJPY/USDCAD on 07-28 are separate *boots* that day, each of
which starts from an empty `symbol_specs`.

**Conclusion: `MAX_SPEC_JUMP = 10` carries essentially zero false-reject risk in
production.** At most one intra-process comparison ever happens per symbol, it is
between two frames taken seconds apart from the same broker snapshot, and the
largest legitimate movement anywhere in the live data is ~2% against a 1000%
threshold. The `* (1 + 1e-9)` tolerance that makes an exactly-10× regrade survive
is correct and load-bearing anyway (mutation M12).

The honest flip side, which the commit message overstates: because a broker
misquote would arrive in the *first* frame with no baseline, the jump guard does
**not** in practice catch "a broker misquoting `tick_value` after a symbol-spec
change" — the §2 rationale it leads with. Against that case only the absolute
envelopes apply. The jump guard's real value is against *unsolicited* HISTORY
frames, i.e. the injection case. That is a legitimate control; it is just a
different one from the one advertised. Recorded as OBS-2, non-blocking.

### The one real false-reject vector is `vm`/`vs <= 0` — see MINOR-1

### Which failure is worse — the asymmetry that justifies wide envelopes

This is the reasoning that should govern any future retune, so I am stating it
explicitly rather than leaving it implicit in the numbers.

**A false accept and a false reject are not symmetric costs.**

- A **false reject** stops **one** pair. It is *loud*: `_reject_specs` logs a
  `RISK` event naming the symbol, the field and the value, and every subsequent
  signal on that pair logs `No broker specs for {symbol}; skipping trade`. It is
  bounded — the other eleven pairs are untouched, no position is opened, no money
  moves. It is recoverable by a restart. Its cost is opportunity cost.
- A **false accept** sizes a **real trade** off poisoned numbers. The whole point
  of §2 is that `ticks_at_risk → 0` drives the next trade to `hard_max_lots =
  5.0` against an intended 1% risk — and `risk_to_stop`/`aggregate_open_risk`,
  the portfolio cap that exists to catch exactly this, compute off the *same*
  poisoned specs and certify it as safe. There is no second line of defence
  behind it. Its cost is real capital, at up to 5.0 lots, on a live account.

So the envelopes should be set **wide enough that no legitimate frame is ever
rejected, and no wider**. That is exactly what the shipped values do: every one
of the 12 live pairs clears the nearest edge by ≥100× on `val` and ≥10× on `ts`,
while the envelope still bounds the poisoning attack to the `val = 1e-4`,
`ts = 100` corner. Tightening them to "look safer" would trade a bounded,
loud, one-pair opportunity cost for a real risk of no rejection at all being
possible — the wrong direction on both axes. The bounds are correctly placed, and
the asymmetry is the reason to leave them alone.

The same asymmetry is why MINOR-1 is a genuine finding and not pedantry: it is
the one place where the implementation rejects on a field (`vm`/`vs`) that
*cannot* cause a false accept, so it buys nothing on the expensive side of the
asymmetry while paying on the cheap side.

### Residual risk: this does not close SEC-05 against a determined attacker

Worth stating so nobody reads S017 as "SEC-05 done". An attacker who can reach
the sockets can send unsolicited HISTORY frames; the jump guard permits exactly
10× per frame and **each accepted frame becomes the new baseline**, so `val` can
be walked `1.0 → 1e-4` in four frames. At the envelope corner
(`val = 1e-4`, `ts = 100`) `calculate_lot_size` still saturates at
`hard_max_lots = 5.0`, and `aggregate_open_risk`/`risk_to_stop` validate it off
the same poisoned numbers. The envelopes cap the blast radius and cost the
attacker a handful of crafted frames; they do not eliminate it. What actually
removes the attacker's reach is the loopback bind — and the remaining closure is
part 3 (HMAC), which §2 deferred deliberately. Correct scoping, but the
sequencing matters: **the bind is the security control here, the bounds are the
robustness control.**

## Findings

No CRITICAL. No MAJOR. Nothing that a remediation pass must fix before this
lands.

**MINOR-1 — rejecting the whole frame on `vm`/`vs <= 0` can dark a pair for an
entire session, and `vm`/`vs` are not part of the threat the session exists to
close.** `vm` and `vs` never enter the sizing divisor: `money_loss_per_lot =
ticks_at_risk * spec['val']` uses only `val` and `ts`. `vm`/`vs` only gate and
round the final lot, and both directions of abuse already fail closed
(`vm` huge → `if adjusted_lots < min_vol: return 0.0`; `vs` huge →
`floor(adjusted/vs)*vs = 0`). So a hostile `vm`/`vs` cannot oversize a trade —
bounding them is defence-in-depth, not the core control.

But rejecting on them is **whole-frame**, so a broker reporting
`SYMBOL_VOLUME_MIN = 0` for a cold or unsynchronised symbol now discards a
perfectly good `tick_value`/`tick_size` along with it. Combined with the
warmup-only cadence established above, that symbol stays spec-less for the
**entire process lifetime** and `calculate_lot_size` returns `0.0` on every
signal until the operator restarts the bot. Before this change the same frame was
accepted and the symbol traded normally on the `0.01` fallbacks.

That this is reachable rather than theoretical is attested by the codebase
itself: there are **two independent pre-existing fallbacks** for exactly this
condition —

```python
# risk_manager.py, calculate_lot_size
min_vol  = spec['vm'] if spec['vm'] > 0 else 0.01   # "guard against a broker reporting 0 to avoid /0"
vol_step = spec['vs'] if spec['vs'] > 0 else 0.01
# trade_manager.py:197-199
min_lot  = spec['vm'] if spec and spec['vm'] > 0 else 0.01
step_lot = spec['vs'] if spec and spec['vs'] > 0 else 0.01
```

Defensive code that specific is normally written after someone saw the zero. Both
fallbacks are now unreachable for any spec that came through
`update_symbol_specs`. `CLAUDE.md` separately warns that a "cold" symbol may
return nothing useful on the first request.

Why this stays MINOR and not MAJOR: it is **spec-mandated** (§2 says "reject …
`vm <= 0` / `vs <= 0`"), so the builder had no discretion and DoD item 2 is
satisfied exactly as written; **all 12 live pairs report `vm = vs = 0.01` in the
tape**, so a zero is not observed on this broker; it fails *closed*, which is this
project's stated
doctrine; it is logged twice (the `RISK` reject event, then
`No broker specs for {symbol}` on every subsequent signal); and the remedy is one
restart. The cheap improvement, for whoever owns the follow-up: treat `vm`/`vs`
as advisory — reject the frame only on `val`/`ts`, and let the existing `0.01`
floors absorb a zero — which strictly dominates the current behaviour because
`vm`/`vs` cannot cause over-risk.

**MINOR-2 — a rejected spec is a trading stop with no Telegram.** `_reject_specs`
emits `log_event("RISK", "SPECS", …)`, which `audit_logger.py:88-103` writes to
the log file and the `audit_log` table. Nothing more. Compare the portfolio cap,
which `CLAUDE.md` says "Telegrams the operator naming the offending row, because
otherwise a total trading stop is indistinguishable from a quiet market". A
rejected spec on a never-specced symbol is the same failure class — that pair
stops trading and the market looks quiet — with strictly weaker notification.
§2 only required a `log_event`, so this is not a DoD miss; it is the obvious next
increment and it is one line.
