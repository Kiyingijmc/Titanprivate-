## Findings

### CRITICAL-1 — verification checks the wrong set; a stale/incomplete pre-panic book makes it silently lie "Verified"

`system_controller.py:2229-2231`:
```python
close_tickets = {int(p.get('t', 0)) for p in self.current_open_positions if int(p.get('t', 0)) > 0}
cancel_tickets = {int(o.get('t', 0)) for o in getattr(self, 'current_pending_orders', [])
                   if int(o.get('t', 0)) > 0}
```
and `_verify_panic_flatten` (`:2284-2287`):
```python
open_tickets = {int(p.get('t', 0)) for p in self.current_open_positions}
pending_tickets = {int(o.get('t', 0)) for o in getattr(self, 'current_pending_orders', [])}
surviving_positions = close_tickets & open_tickets
surviving_orders = cancel_tickets & pending_tickets
```
`surviving_positions`/`surviving_orders` are computed as the **intersection** of the
pre-panic-known ticket IDs with the fresh heartbeat's ticket IDs — never as "does the fresh
heartbeat show anything open at all." If `self.current_open_positions` understates the real
broker book at the moment `/panic` is pressed (stale heartbeat, EA reconnect gap, a position
that filled between the last processed heartbeat and the panic command), then:
1. `close_tickets` is empty or incomplete for that ticket, so `close_all_market_orders()`
   (`:2293-2300`, which also iterates `self.current_open_positions`) never sends it a
   `CLOSE_POS` at all — not even an attempt.
2. The next fresh heartbeat in `_verify_panic_flatten` **will** contain that ticket in
   `open_tickets`, but `close_tickets & open_tickets` is empty (the untracked ticket was
   never in `close_tickets` to begin with), so `surviving_positions` comes back empty.
3. `trigger_panic` sends **"✅ Global Flatten Verified"** while a real, fully open,
   never-touched position sits on the broker.

This is not a hypothetical edge case in this codebase: heartbeat-staleness masking an open
position is the exact failure class recorded in `demo-forward-test` history (a stopless
GBPJPY position left unmanaged for 3h21m by a dead EA heartbeat while "every ordinary health
check looked fine"). This session's own docstring for `_verify_panic_flatten`
(`:2255-2266`) frames the whole feature around exactly this danger — "a command being sent
is not evidence it took effect; only a fresh HEARTBEAT is" — but then implements the
comparison against the pre-panic snapshot instead of the fresh heartbeat's actual contents,
reintroducing the same "operator gets false assurance" bug one layer up. It also does not
match the linked ctrl-02 spec's own words: *"report the **OBSERVED position count**"* — the
observed count from the fresh heartbeat, not an intersection against what was known before
panic fired.

Fix direction: after each fresh heartbeat, flag survival based on what the heartbeat
actually shows (e.g. `surviving_positions = open_tickets` outright, or at minimum
`close_tickets | (open_tickets - {legitimately pre-existing, non-panic-targeted tickets})`
— but since `/panic` is meant to flatten *everything*, checking "is `open_tickets`/
`pending_tickets` non-empty" is the correct, simpler check and also closes this gap).

No test exercises "the real broker book contains a ticket `current_open_positions` didn't
know about at panic time" — all three new tests construct `close_tickets`/`cancel_tickets`
consistent with what the fresh heartbeats show, so this gap is untested as well as unfixed.

**failure_scenario**: EA reconnects after a brief drop; the last processed heartbeat before
`/panic` shows `current_open_positions = []` even though a position is actually open on the
broker (filled just before/during the gap). Operator hits `/panic`. `close_all_market_orders()`
sends zero `CLOSE_POS` commands (nothing in `current_open_positions` to iterate). The next
fresh heartbeat correctly reports the real open position, but `close_tickets (∅) & open_tickets
({that ticket})` = ∅, so `_verify_panic_flatten` returns no survivors and `trigger_panic`
telegrams "✅ Global Flatten Verified: Closed 0 | Cancelled 0" while the position remains
fully open and was never even attempted.

### MAJOR-1 — the "nothing else reads the socket while it awaits" invariant is false for the GUI `/panic` path, and the main loop's 1ms cadence makes the verifier lose that race almost every time

`_verify_panic_flatten`'s docstring (`:2260-2262`) asserts: *"this coroutine runs on the
same single-threaded loop as `run()`'s poll, so nothing else will read the socket while it
awaits."* That is true for the Telegram path (`telemetry.py:198` is awaited inline from
inside `run()`'s own loop body at `system_controller.py:576`, so `run()`'s own Task is
suspended for the whole call). It is **not** true for the GUI/web panic path:
- `src/ops/web/commands.py:22-24` calls `await controller.trigger_panic()` from inside a
  FastAPI request handler.
- `src/ops/web/server.py:222`: `return asyncio.create_task(server.serve(sockets=[sock]))` —
  the embedded control API runs as its **own asyncio Task** on the same event loop, not
  inline inside `run()`'s Task.
- `run()`'s own loop iterates on an effectively 1ms cadence
  (`system_controller.py:643`: `await asyncio.sleep(0.001)`), calling
  `self.bridge.poll_data()` every iteration (`:583-586`).

`bridge_zmq.py`'s `poll_data()` reads directly off the raw ZMQ PULL socket with `NOBLOCK`
and no locking (`src/execution/bridge_zmq.py:101-118`). Because `run()`'s Task polls that
socket roughly every millisecond while `_verify_panic_flatten`'s own poll is paced at
`poll_interval=0.25s` and only fires once per its own loop pass, `run()`'s Task will almost
always drain any pending HEARTBEAT off the socket first when a GUI-triggered panic is in
flight concurrently. `_verify_panic_flatten`'s own `poll_data()` call then sees an empty
batch, `got_heartbeat` stays `False`, and it just sleeps — `heartbeats_seen` never advances,
and after the 6s timeout it returns the **original, unmodified** `close_tickets`/
`cancel_tickets` as "surviving," even if `run()`'s Task already processed the real heartbeat
and the book is actually flat (`self.current_open_positions`/`current_pending_orders` are
correctly updated by that other Task's own call into the same `_process_incoming_data`, but
`_verify_panic_flatten`'s branch never re-reads them because its own `got_heartbeat` gate
never trips).

Net effect: a `/panic` triggered from the GUI/web control panel will, in practice, almost
always report `🆘 PANIC FLATTEN UNVERIFIED — book still exposed` regardless of whether the
flatten actually succeeded, because the verifier is starved of the heartbeat it needs by the
main loop's much tighter polling cadence running as a concurrent Task. This doesn't create a
false-safety report (the bias is toward over-escalating, not under-escalating, so it's
fail-safe in direction), but it does mean the feature is effectively non-functional through
one of its two production entry points, and worse, it trains operators to distrust/ignore
the "book still exposed" alert precisely because it fires even on successful GUI panics.

**failure_scenario**: operator presses "Panic" in the web dashboard (`commands.py:22`,
requires `confirm: true`). `close_all_market_orders`/`cancel_pending_orders` succeed and the
broker book actually goes flat. `run()`'s Task (polling every ~1ms) picks up the next
heartbeat and correctly zeroes `current_open_positions`/`current_pending_orders` before
`_verify_panic_flatten`'s own (0.25s-paced) `poll_data()` call gets a chance at it. After 6s,
`_verify_panic_flatten` times out having seen zero heartbeats itself, and `trigger_panic`
telegrams "UNVERIFIED — book still exposed" listing the original tickets, even though the
book was actually flattened successfully several seconds earlier.

No test constructs a real concurrent `asyncio.create_task` scenario for either the web
server Task or the main-loop Task, so this race is untested; the existing three
`panic_verification` tests all call `trigger_panic()` directly on a bare controller with no
competing consumer of `bridge.poll_data()`.

## Verdict rationale

Item 1 of the session's own DoD (EMERGENCY manages like PAUSED) is correctly and cleanly

path silently report success on an unmanaged, never-touched position (CRITICAL-1) — the
precise failure mode ctrl-02 and this session exist to close. The GUI panic entry point
additionally races with the main loop's own polling and will typically starve itself of the
verification it depends on (MAJOR-1).

## Findings (round 2)

### MAJOR-1 — the 6.0s budget cannot deliver the two-heartbeat confirmation the code documents, and a flatten still in flight at the single observed heartbeat telegrams a false "book still exposed"

`src/core/system_controller.py:148-151` justifies the new constant as:

```python
# How long trigger_panic waits for fresh HEARTBEATs before it declares the
# flatten unverified (see _verify_panic_flatten). ~2 EA heartbeats at the
# 5s publish rate, with slack for the close/cancel round trip.
PANIC_VERIFY_TIMEOUT_S = 6.0
```

That arithmetic is wrong. The EA publishes on a free-running 5s cycle
(`mql5_bridge/Experts/Titan_Gateway.mq5:98`: `if(GetTickCount64() - last_heartbeat > 5000)`),
and `/panic` arrives at a uniformly random phase of that cycle. If the first fresh heartbeat
lands at `t₁ ~ U(0,5)`, the second lands at `t₁ + 5`, so a 6.0s window contains **two**
heartbeats only when `t₁ ≤ 1.0s` — roughly 20% of phases. Four times out of five the loop
(`:2308`: `while heartbeats_seen < 2 and time.time() < deadline`) reaches its deadline having
seen exactly one, and the second heartbeat that the docstring says exists specifically for
the in-flight case ("a close/cancel may have been in flight when the first one was
captured" — the rationale retained through both rounds) is simply unreachable.

That matters because the flatten is not instantaneous. The EA consumes **one** PUSH command
per `OnTimer` tick (`Titan_Gateway.mq5:17` `InpTimerMS = 10`, `:72-73` a single
`socket_pull.Recv()` per tick), each `CLOSE_POS`/`CANCEL` round-trips to the broker inside
that same handler, and `SendHeartbeat()` runs in the *same* `OnTimer` (`:97-100`) — so
heartbeats interleave between individual position closes and can legitimately capture a
half-flattened book.

**failure_scenario**: four positions open; operator hits `/panic`. The EA is mid-flatten when
its heartbeat fires at `t₁ = 1.8s`, reporting two tickets still open. `_verify_panic_flatten`
records `heartbeats_seen = 1`, `surviving_positions = {#c, #d}`, and loops. The next heartbeat
is due at `t = 6.8s`, past the 6.0s deadline, so the loop exits on the deadline. Because
`heartbeats_seen != 0`, control falls to the `else` branch (`:2267-2273`) and the operator is
telegrammed `🆘 PANIC FLATTEN UNVERIFIED — book still exposed — Positions still open: #c, #d`
for a book that actually went flat at `t ≈ 2.2s`. The bias is fail-safe (over-escalating), but
this is exactly the operator-trust harm round-1 MAJOR-1 was raised for: an alert that fires on
successful panics is an alert operators learn to ignore, and it is the *only* signal
distinguishing a real unflattened book from a healthy one.

Fix direction: don't just bump the constant to `2 × 5s + slack` — see MINOR-2, which that
makes worse. Either restart/extend the deadline from the *first observed* heartbeat (so the
budget measures "two heartbeats after I started looking", which is what the docstring
describes), or move the confirmation off the blocking path entirely (see MAJOR-2). At minimum,
the comment at `:148-151` must stop asserting a guarantee the value does not provide.

### MAJOR-2 — the escalation is one-shot; after it fires nothing ever re-checks, and the bot then sits in EMERGENCY indefinitely with a live book

`trigger_panic` sends one message and returns (`:2267-2273`). No state is left behind, no
caller re-runs the verification, and there is no periodic re-check anywhere: `grep` for
`_verify_panic_flatten` finds `trigger_panic` as its only caller. So the entire operator-facing
consequence of a genuinely failed flatten is a single Telegram at `t ≈ 6s`, after which the
system is permanently silent about a book it has itself declared unverified — while
`self.state` stays `EMERGENCY` forever (nothing clears it except a manual
`set_system_pause`, `:2196`).

This diverges from the convention this same file has established for precisely this class of
problem — a fire-and-forget PUSH command whose refusal is visible only as the ticket surviving
in later heartbeats:

- `_escalate_stuck_cancels` (`:1302-1319`), throttled by `DD_CANCEL_ALERT_INTERVAL_S = 1800`
  (`:131`), re-alerts while the condition persists and re-arms when it clears.
- `_escalate_news_cancels` (`:920-948`), throttled by `NEWS_CANCEL_ALERT_INTERVAL_S = 1800`
  (`:107`), same shape.
- `_alert_uncomputable_book` (`:1114-1141`), throttled by `UNCOMPUTABLE_ALERT_INTERVAL_S`
  (`:88`), same shape.

The comment at `:121-131` records why: those repeats were added by RS022 round-2 MAJOR-1
because a one-shot notice provably was not enough for an unconfirmed CANCEL. A panic that
failed to flatten is strictly the more severe instance of the same failure, on a bot that
memory records as running unattended since 2026-07-28.

I acknowledge the literal DoD sentence ("verify the flatten outcome against the next
heartbeat(s) and escalate if positions remain", `docs/sessions/_BACKLOG.md:152`; ctrl-02's
"Wait 1-2 heartbeats; report the OBSERVED position count; escalate if positions remain",
`:25`) is satisfied by a single escalation, so this is a convention/robustness gap rather than
a missed requirement. It is still actionable: the remediation pass should either add the
throttled repeat (the surviving tickets are already computed, and the HEARTBEAT branch at
`:1592-1605` is the natural place to re-check them) **or** record an explicit, reasoned
decline in the session report so the divergence from the file's own escalation convention is
a decision rather than an oversight.

**failure_scenario**: `/panic` fires on a Sunday-closed market; the EA rejects every
`CLOSE_POS` with retcode 10018 (invisible to Python — see project memory on EA command
rejects). At `t ≈ 6s` one Telegram says "book still exposed: #42". The operator is asleep, or
the Telegram send fails (network flap — the same WSL DNS flap that already breaks the news
feed hourly). Nothing re-alerts. Twelve hours later the position is still open, still in
EMERGENCY, and the only trace that the panic did not work is a message that may never have
been delivered.

### MINOR-1 — the panic outcome is Telegram-only; nothing is written to the audit log

Neither the verified branch (`:2261-2266`), the escalation branch (`:2267-2273`), nor the
no-heartbeat branch (`:2249-2260`) touches `self.logger`. Every comparable alarm in this file
pairs the Telegram with a `log_event` for the forensic record — `:937-941` (`WARN`/`NEWS`),
`:1315-1319` (the DD stuck-cancel escalation). Combined with MAJOR-2, a failed panic whose
single Telegram was not delivered leaves **no** durable evidence anywhere that the flatten was
unverified.

### MINOR-2 — `trigger_panic` now stalls the main loop for the whole verification window on the Telegram path

`/panic` is dispatched from `telemetry.poll_commands()`, awaited inline from `run()`'s own
loop body at `:581`. The verification therefore suspends `run()` for up to
`PANIC_VERIFY_TIMEOUT_S`, freezing section A (Sync Guard), section B (the dead-EA
`_reboot_terminal` watchdog), section E (ghost cleanup + news pending sweep), section F
(reporting) and section G (the 10s `PING` + `sd_notify("WATCHDOG=1")` at `:641-644`, whose
`second % 10 == 0 and microsecond < 50000` window a 6s stall can skip outright). In-trade
management is not affected — `_verify_panic_flatten` drains the bridge itself and routes every
message through `_process_incoming_data` (`:2309-2312`), which was the right call. This is
worth recording deliberately rather than by accident, and it is the second reason not to fix
MAJOR-1 by simply widening the timeout to ≥11s. Historical context: the Telegram phase-1 plan
recorded "`/panic` stays instant"
(`docs/superpowers/plans/2026-07-11-telegram-phase1.md:16`).

### MINOR-3 — the timeout value now exists in three places, one of them dead

`PANIC_VERIFY_TIMEOUT_S = 6.0` (`:151`); `getattr(self, 'PANIC_VERIFY_TIMEOUT_S', 6.0)`
(`:2244`) — the class attribute always exists, so the `6.0` fallback is unreachable and the
`getattr` itself is redundant (a plain attribute read supports the instance-shadowing the
tests use); and `timeout_s=6.0` as `_verify_panic_flatten`'s signature default (`:2276`).
Collapse to the one named constant so a future change to the heartbeat cadence has a single
edit point.

## Verdict rationale

The remediation is real work, not a paper fix: round-1's CRITICAL-1 and MAJOR-1 are both
genuinely closed, the freshness key chosen (`last_book_snapshot_at`) is the correct one rather
than the convenient one, the new `heartbeats_seen == 0` branch closes a hole neither round-1
finding named, and the new tests reproduce the actual two-Task race instead of asserting on a
mock. Item 1 of the DoD remains clean.

What is left is the timing envelope around that logic. The 6.0s budget contradicts its own
justifying comment and makes the second-heartbeat confirmation — the very mechanism that
distinguishes "still flattening" from "flatten failed" — unavailable four times out of five,
producing false "book still exposed" alerts on successful panics (MAJOR-1). And the escalation
that does fire is a single message with no repeat and no audit-log companion, on the one
condition in this system where silence is most expensive (MAJOR-2, MINOR-1). Neither is a
false-safety defect, but both undermine the operator signal this session exists to create, and
both are cheap to fix — plausibly by the same change, moving the confirm/escalate onto the
heartbeat-driven pattern the file already uses three times over.
