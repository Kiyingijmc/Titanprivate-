## Does it work?

**`projection.fold` (§1.3 "project(snap); apply tail events").** `tradebot/core/
projection.py:123-169` is exactly the pure half the module docstring promises: no
`sqlite3`, no import of `event_log` (asserted by its own `TestModuleIsPure`, which parses
the module's AST rather than trusting the docstring — a good, self-enforcing test). The
per-schema reducer registry (`register_reducer`/`reducer_for`/`registered_schemas`) refuses
a silent overwrite by a *different* function bound to an already-registered schema
(`:81-89`) but is a no-op for re-registering the same one (module re-import safe). The two
skip rules pass3-systems.md §2 and this session's own scope call for are both correct and
tested: an envelope with no registered reducer is logged-and-ignored, never an error
(`:149-151`, `test_a_schema_with_no_reducer_is_skipped_not_an_error`); a `snapshot.projection`
row is *never* re-folded, proven by a reducer deliberately bound to that schema that must
never fire (`test_snapshot_rows_are_never_refolded`). `state[LAST_SEQ]` advances past
skipped rows (`:157-159`, `test_last_seq_advances_past_skipped_rows_too`) — correct, since a
resume from a stalled watermark would re-offer unmapped events forever — and never regresses
(`test_the_watermark_never_goes_backward`) or moves for a `seq=None` envelope
(`test_envelopes_without_a_seq_leave_the_watermark_alone`). The folded state carries no
`row_hash`/`prev_hash`/`chain_head` key (`test_the_folded_state_carries_no_chain_hash_fields`)
— correct per `Envelope`'s actual field set, which I confirmed against
`tradebot/core/events.py:154-165` has no such field. `SNAPSHOT_SCHEMA` is duplicated rather
than imported (deliberate, to keep `sqlite3` out of this module) and a guard test pins it
equal to `event_log.SNAPSHOT_SCHEMA` so the two spellings cannot drift apart unnoticed.

**`recovery.verify_and_replay` (§1.3 boot pseudocode, §1.4/F-015).** `tradebot/core/
recovery.py:217-260` takes the boot lock first, then `verify_chain()`, then resolves the
newest retained snapshot (`_initial_state`, `:263-282`) and folds only the tail on top of it
(`event_log.read(from_seq=snapshot_seq+1)` when a snapshot exists, `from_seq=0` otherwise) —
matching "walk chain from snap.seq to head" literally. A `RecoveryRequired` from either
`verify_chain()` or `_initial_state`/`_snapshot_state` is caught in one place and turned into
`BootResult(status=RECOVERY_REQUIRED, state=None, chain_head=None, ...)` — never a partial
state (`BootResult.state` is genuinely `None`, not `{}`, confirmed by
`assert_recovery_required`'s `assertIsNone(result.state, ...)` and by
`test_no_drill_produces_a_usable_state`, which reruns the check without assuming any
particular error message). Any *other* exception (a real bug, an unreadable file) releases
the boot lock before re-raising (`:246-251`) so a non-integrity failure cannot strand the
lock — correct, and distinct from the integrity-failure path, which keeps the lock held on
purpose (the refused boot still owns the log for exit-management, per the module's own
docstring rationale, and `test_a_refused_boot_keeps_the_lock` proves a second
`acquire_boot_lock` is refused while it is up).

I re-derived the five re-run drills (`TestCorruptionDrills`) against `event_log.py`'s actual
`verify_chain` implementation: truncated tail (`DELETE ... WHERE seq>4`) hits the "chain
tail ends at seq N but the recorded head is..." branch (`event_log.py:619-623`); payload
bit-flip and `row_hash` bit-flip both hit the recompute-mismatch branch (`:610-613`);
mid-chain row delete hits the seq-gap branch (`:585-588`); the three sidecar-corruption
shapes (tampered-but-valid-gzip, damaged stream, missing file) all route through
`_verify_sidecar` (`:625-640`), which `verify_chain` calls for every retained
`snapshot.projection` row. None of the five can reach a clean boot — that is the module's one
governing property, and it holds under trace.

**Boot lock / F-015 (`TestBootLock`).** `acquire_boot_lock` opens `<db_path>.boot.lock` and
takes `flock(LOCK_EX | LOCK_NB)` (`:143-152`); a second acquire on the same path fails
immediately (measured under 0.5 s, so a pass cannot be a `busy_timeout` wait wearing a lock's
clothes — a nice, specific guard against a flaky-looking false positive). Crucially,
`test_the_boot_lock_does_not_change_the_event_log_contract` opens a *second* `EventLog` on
the same `db_path` while the boot lock is held and proves it still appends successfully —
confirming the module docstring's claim that `EventLog`'s own construction/`busy_timeout`
contract was left untouched; the boot lock is strictly additional, not a replacement for
M0-3's contention backstop. This is the "second-writer attempt fails a test" acceptance line
from the backlog, discharged, and discharged at the *boot* layer specifically (stronger than
M0-3's interleave-safely guarantee, and the test suite explicitly documents why the two are
different properties rather than conflating them).

**Determinism (`TestDeterminism`).** Two independently built logs from the identical event
stream (with a *shared* `SimClock`, so `ts_ingest` cannot be the source of any accidental
divergence) boot to `canonical_json`-identical state and identical `chain_head`
(`test_identical_streams_boot_to_identical_state_and_chain_head`); a genuinely differing
payload diverges both (`test_a_differing_payload_diverges_both`). This is the backlog's
second acceptance line, discharged.

**Snapshot/sidecar resolution.** `_snapshot_state` (`recovery.py:285-325`) resolves a
sidecar's relative path against `event_log.db_path.parent`, while `EventLog._verify_sidecar`
resolves the same sidecar by basename inside its own `self._snapshot_dir`
(`event_log.py:625-628`). I checked these agree: `EventLog._snapshot_locked` records the
sidecar path via `_relative_path(path, self.db_path.parent)` (`event_log.py:701-705`), and
the *default* `snapshot_dir` is exactly `db_path.parent/"snapshots"`, so the two resolutions
land on the same file for the default (and, for the every-test case here, only) configuration.
The module's own docstring is honest that this is a second, independent hash check rather
than a rerun of the first (`verify_chain` already proved the sidecar's SHA-256; this "costs
one read and closes the gap between the two resolutions") — a defensible belt-and-suspenders
choice, not a claimed guarantee it doesn't have.

## Findings

None survive review. I looked hard at the two places most likely to hide a defect in this
kind of module — the boundary between `verify_chain()`'s success and `_initial_state()`'s own
`RecoveryRequired` raises (both route through the same `except` clause, so neither can leak
a partial state), and the archive-boundary concern the *prior* review (`RS004.md`, MINOR)
flagged as "about to be load-bearing" for this session's `verify_and_replay`. On inspection
that concern does not land as a defect here: `EventLog.verify_chain()`'s own
`expected_first = max(from_seq, archived_through + 1)` (`event_log.py:575`) already accounts
for an archived prefix on the *seq* axis, and `recovery.verify_and_replay` calls it with the
default `from_seq=0`, so archived logs still verify correctly through this path — RS004's
MINOR (no *hash* anchor across the archive boundary) is a real, still-open gap, but it lives
entirely inside `event_log.py`'s own verification, which this session correctly left
untouched; `recovery.py` neither introduces nor worsens it, and folding it into project
memory to catch whenever `event_log.py` is next touched is the right call rather than
in-scope work here.

## Observations (not findings)

- **Deliberate scope simplifications are documented, not silently dropped.** The §1.3
  pseudocode's feature-restart-policy (§4.5/F-014) and `STARTUP` broker-truth reconcile
  (§3.3) steps are explicitly *not* implemented, with a stated reason (the subsystems they'd
  call — `tradebot/features/`, a broker adapter — don't exist yet) and a stated consequence
  (neither is stubbed; they hook in later). This matches the backlog line for m0-4, which
  names only `projection.py` + `recovery.py` + sole-writer enforcement, not these two later
  steps.
- **`recovery.py` duplicates `event_log.py`'s private `_DECOMPRESS_ERRORS` tuple**
  (`recovery.py:81` vs. `event_log.py:97`) rather than importing it, even though `recovery.py`
  already imports several names from `event_log.py` — unlike `projection.py`'s duplication of
  `SNAPSHOT_SCHEMA`, there's no "keep sqlite3 out of a pure module" reason for this one, since
  `recovery.py` is already coupled to `event_log.py`. Purely cosmetic (both tuples are
  identical and neither is exported for reuse — importing a leading-underscore name across
  modules is itself the kind of thing worth avoiding), not worth a remediation pass on its
  own.
- **`BootLock`/`BootResult` are both context managers**, and the test suite exercises both
  the `with` form and manual `release()`/`addCleanup` — no leaked lock file descriptors
  across the 44 tests as far as I can trace (every `boot()`/`acquire()` helper in
  `RecoveryTestCase` registers its own cleanup).
- Test-file placement and the "why flat, not `tests/unit/tradebot/`" rationale are repeated
  verbatim from S003/S004's docstrings — consistent, and still correct.

## Three-axis readiness

- **Does it work:** yes, on every acceptance line this session was graded against — the
  backlog's own line (second-writer-fails-a-test, chain-head determinism), the five
  corruption drills re-proven one layer up, and the pure-fold contract `projection.py`
  claims for itself. Hand-traced clean; unrun `VERIFY_CMD` is a disclosed open item, not a
  finding.
- **Is it safe:** yes. Purely additive — four new files, zero existing files touched, zero
  new dependencies. Nothing under `src/` (the live v14 ZMQ system) is reachable from this
  code, and nothing in it is wired into anything that runs today.
- **Is it worth it:** yes. This is the money-truth substrate's boot half — the actual place
  `RECOVERY_REQUIRED` stops being a signal and starts being a refusal to trade — landed with
  the same care as M0-3, a clean scope fence (tighter than S004's, which needed one
  test-hygiene fix elsewhere), and a test suite that reasons about what it is and is not
  proving (e.g. distinguishing "second boot refused immediately" from "second writer
  interleaves safely" rather than treating them as the same guarantee).

## Verdict

Clean, additive, scope-disciplined work that delivers exactly what the backlog asked for and
nothing else. I found no CRITICAL, MAJOR, or MINOR defect in `projection.py`, `recovery.py`,
or their tests after tracing every acceptance line, every corruption drill, and the one
carry-over concern the prior review flagged as relevant to this session. The only open item
is procedural, not a code defect: `VERIFY_CMD` must still be run for real by whoever has
execution rights in this environment.
