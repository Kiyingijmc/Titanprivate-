## 1. Audit methodology + scope

Each seat performed a domain sweep of all six docs, then the board cross-examined every claim in three passes: (1) **unit/math audit** — every formula's operands traced to a defined unit and source; (2) **race/failure enumeration** — every asynchronous boundary (human↔bot, bot↔broker, process↔process, clock↔clock) walked through interleavings; (3) **money-path audit** — every place a currency amount, risk figure, or performance number is produced, the Auditor demanded the reconciliation path and the failure-to-reconcile behavior. Claims of the form "X is handled" without a mechanism were treated as gaps. The Auditor applied the standing rule: an optimistic assumption survives only if a seat can name the mechanism that makes it true.

Severity definitions: **CRITICAL** = would lose money, corrupt state, or silently violate a locked requirement; **HIGH** = materially degrades edge or operations; **MEDIUM** = design debt, fix before building that component; **LOW** = polish.

Disposition key: `RESOLVE-IN-PASS-N` (assigned to the pass owning that domain: 2 strategies/quant · 3 risk/lifecycle · 4 execution/broker · 5 architecture/state · 6 interfaces/ops · 7 validation/learning · 8 synthesis), `RESOLVED-HERE` (fix specified in this document; later passes adopt it), `OPEN-FOR-HUMAN` (product/deployment decision; decision matrix required).

## 3. Detailed write-ups — CRITICAL and HIGH

### F-001 — Partial fill during pending confirmation (CRITICAL)

The Algo-Bot Developer opened with the observation that 02§B3's "confirm-while-resting" is the single most dangerous cell in the mode table: it deliberately places a live order into the market *before* the human decision, which is good for fill quality and fatal for state integrity, because the broker does not wait. The Frontend Architect initially pushed back — "the veto just cancels the order" — until the Dev walked the partial-fill interleaving: cancel removes only the unfilled remainder; MT5 returns a position for the filled fraction regardless. The Quant noted the subtle second-order effect: partial fills at a passive band are adversely selected (F-012), so the orphaned positions will skew losing. The board resolved it structurally rather than procedurally: fills are facts, so the state machine must have fill edges out of AWAITING_CONFIRM, the risk budget must be debited at placement (else a resting order is invisible risk), and veto-after-fill needs a deterministic default (close the filled fraction immediately, at market, logged `VETO_AFTER_FILL`). The Auditor's condition for sign-off: the confirmation card must visibly change if a partial fill occurs mid-decision — a human approving "a signal" that is already 40% a position is approving something materially different, and the audit trail must show what they saw.

### F-002 — Netting accounts vs multi-child tranches vs broker-side stops (CRITICAL)

The Auditor flagged 03§B6's checkbox — "netting… handled in the adapter (bookkeeping preserved per child tranche)" — as the document's largest claim-to-mechanism gap: three locked design commitments (per-child tranche exits 01§5.3, broker-side hard stop per position 02§A5, opposing children coexisting) are jointly unsatisfiable on a netting account, where the broker maintains one position per symbol with one SL/TP slot. The Algo-Bot Developer confirmed from MT5 mechanics: on netting, an opposing child's entry *is* a partial close of the other child's position; there is no adapter cleverness that undoes this. The Architect proposed synthetic stops (bot-side watchers per tranche), which the Networking seat immediately attacked: synthetic stops die with the bot, which is exactly what 02§A5 exists to prevent. Resolution: v1 discovery gates on account type — hedging accounts get the full model; netting accounts run a degraded, honest mode (one child position per instrument; opposing intents become conflict events). The full synthetic-tranche ledger with an aggregated broker stop at the worst-case level is deferred to Pass 4 as an explicit design, not a checkbox. Marked OPEN-FOR-HUMAN because "degraded mode" is a product decision: some operators' only account option is netting.

### F-003 — Viability formula: mixed units, wrong numerator (CRITICAL)

The Auditor red-teamed the formula the docs call "this single rule prevents the classic failure" and found it cannot compute: `median_spread` arrives in price units, `commission_ticks` in ticks, `expected_slippage` in neither-stated, and the numerator — "avg win distance" — is not an edge. The Quant quantified the second error with the register's example: a 30%-win-rate trend child's viability is overstated by two orders of magnitude when losers are ignored, meaning the gate would *never* fire for exactly the children whose costs matter most. The Strategist added the market-side reading: cost-blindness is the number-one retail killer named in the project's own charter, and this formula is the charter's enforcement mechanism — it must be airtight. Resolved here: all terms in ticks; numerator is pre-cost gross expectancy per round trip from the same backtest evidence G1 consumes; and — the Auditor's insistence — the threshold "4" is void, because it was implicitly calibrated to the wrong numerator; Pass 7 recalibrates (starting hypothesis 1.5–2.0, since a strategy netting less than ~1.5× its round-trip cost has no margin for estimation error). The spread-gate's second line (03§A2) inherits the same fix.

### F-004 — Event log: source of truth without integrity engineering (CRITICAL)

The Chief Systems Architect raised this one against his own preferred pattern: event sourcing is only as trustworthy as the log's integrity engineering, and docs 02/04 specify replay while specifying nothing about corruption, truncation, growth, or backup. The Auditor sharpened it into an accounting statement: an append-only journal with no completeness check is not an audit trail, it is a diary. Concrete holes: no hash chain or sequence-gap detection (a truncated log replays *cleanly* into a wrong projection), no snapshotting (replay time grows without bound — the recovery drill will pass in month 1 and time out in month 18), no off-box backup (VPS disk death = total loss of the source of truth), and the CI recovery drill (05§C) only rehearses kill-9, i.e., the case SQLite already handles well. The Backend Architect noted the fix is cheap at design time: `seq` + `prev_hash` columns, snapshot events, checkpoint discipline, daily backup, and a corruption drill that truncates and bit-flips. The board's binding rule for Pass 5: on any boot-time integrity failure, the core must refuse to trade and reconcile from broker + last good snapshot with human ack — never "best-effort replay and go".

### F-005 — No margin/notional limit; breakeven frees infinite budget (CRITICAL)

The Auditor challenged the sentence celebrating breakeven-freed budget as "a nice emergent property": it is also a hole through which unbounded leverage flows, because risk-to-stop is the *only* exposure metric in doc 02 — margin and notional appear nowhere. The Swing Trader made it concrete: a good trend month is precisely when many positions ride at BE, so the system is designed to be maximally levered at maximum complacency; a gap (F-011) then hands liquidation order to the broker's stop-out engine, which closes positions by its rules, not the bot's — realized losses have no relationship to the per-child stops the whole risk chapter is built on. The Quant initially argued BE positions are genuinely risk-free to-stop; the Auditor's rebuttal — "risk-to-stop assumes the stop fills at the stop" — ended the debate, since that assumption is exactly what fails in the tail. Resolution (Pass 3): margin-utilization cap (~25%, hypothesis), per-class notional caps, and a gap-stressed risk figure in which held-over-close positions count at k× distance-to-stop. BE positions keep consuming margin/notional budgets forever.

### F-006 — Sessions vs DST vs broker server time (HIGH)

The Networking specialist and the Day Trader jointly raised the audit's most bankable calendar bug: every session-scoped child (M1, M2, M4, T4) and the daily breaker use session words with no timezone anchor, while MT5 brokers commonly run server time at UTC+2/+3 pegged to the **US** DST calendar. For the ~2–3 weeks each spring and autumn when US and EU transitions are offset, any broker-server-time session table is one hour wrong for London, and Tokyo (no DST) drifts seasonally against both. The Day Trader supplied the P&L mechanism: M1 fading "Asian" ranges one hour into London open is fading the day's most directional flow with a mean-reversion sizing model — a strategy-inverting error, twice a year, silently. The Strategist noted it also poisons research: backtests using a fixed-offset session label learn a smeared session. Resolution (Pass 4): sessions computed from IANA zones per market; broker server offset discovered *and continuously verified* against tick timestamps; the bot owns its D1/weekly boundaries; the two mismatch windows become named test cases.

### F-007 — SPEC_CHANGED with open positions (HIGH)

The Algo-Bot Developer credited 03§B1 for noticing that brokers change specs silently, then pointed out the doc stops at "raise an event". A `stops_level` increase before news — a real broker behavior, often deliberate — can make the attach-stop-on-fill call fail for an already-resting entry, producing a stopless position in direct violation of 02§A5; a `tick_value`/`contract_size` restatement invalidates the open-risk ledger until someone recomputes it, and nothing in the docs recomputes it. The Auditor classified this as a reconciliation gap: specs are an input to money math, so a spec diff must trigger re-derivation of everything downstream, not a log line. Resolution: a spec-diff impact analyzer with per-field severity (register row), and the rule that SPEC_CHANGED while positions are open escalates to CRITICAL alerting.

### F-008 — Three actors race one confirmation (HIGH)

The Backend Architect mapped the actor set on a single AWAITING_CONFIRM signal: human CAS (from either interface), the hybrid-timeout worker, and the expiry sweeper — and observed that the spec's own timeout formula, `min(10min, 25%·validity)`, *concentrates* these events near each other by construction. The CAS claim in 02§B5 covers double-resolution between GUI and Telegram but not timeout-vs-human-vs-expiry, which live in different processes under F-015's lock contention. The Frontend Architect added the human-factors requirement: when a human "wins" a race they actually lost (tap lands after timeout-execute), the UI must tell them the truth (`resolved_by: timeout`) or they will build a false model of their own control — dangerous in an interface whose whole purpose is decision-making under time pressure. Resolution: one serialized transition owner in the core; timeout and expiry become queued *requests*; expiry is evaluated inside the handler on event-time so a same-instant execute never beats valid_until.

### F-009 — Interface outage converts hybrid to auto (HIGH)

The Infra seat asked the simplest adversarial question of the session: "who checks that anyone *saw* the card?" Nobody — delivery is fire-and-forget in 05§A2, and hybrid's default `timeout: execute` for trend children means an unseen card is an executed trade. A Telegram platform outage (they happen; minutes-to-hours) plus an unattended GUI silently degrades every hybrid child to full-auto, which the Auditor flagged as a *silent mode-contract violation* — the operator chose hybrid, the system delivered auto, and no log line says so. The Master Strategist offered the counterargument that timeout-execute exists precisely so an absent human doesn't block regime-gated signals; the board's synthesis: absence-by-choice (saw it, ignored it) and absence-by-outage (never delivered) are different states and must be distinguished. Resolution: delivery-acks; unacked cards degrade timeout to `skip` (fail-closed) and raise WARN; per-child opt-out for operators who genuinely want auto-fallback.

### F-010 — Regime-flip cancel races the fill (HIGH)

The Algo-Bot Developer, from production scar tissue: every "cancel the resting order" design eventually meets the fill that got there first, and 01§2's flow (`invalidation() → order cancelled`) has no arm for it. The dangerous part is not the race — it's that the signal has already transitioned to INVALIDATED locally, so the arriving fill has no live signal to attach to; depending on implementation, the position escapes the exposure ledger and `manage_position()` entirely. The Quant added the statistical insult: fills that beat a regime-flip cancel are maximally adverse (the regime flipped *through* the level), so the unmanaged-orphan population is also the worst-performing population. Resolution: cancels are requests; only broker-confirmed outcomes transition state; a dedicated `FILL_AFTER_INVALIDATION` path adopts the position, attaches the frozen stop, engages the child, and tags the trade for the learning loop.

### F-011 — Weekend gaps vs the sizing identity (HIGH)

The Swing Trader owned this one: the entire sizing chain (02§A1) rests on `loss ≈ risk_amount`, which is a *fill assumption*, and the children that define the book (T1 D1, T3 W1) hold through the exact windows where the assumption fails — weekends and exchange closes — while the weekend-flatten rule is optional config scoped to "CFDs". Historical gap events (register row; literature-informed) have opened index CFDs multiple ATRs through stops. The Quant's framing: the 8% account budget is an L1 estimate of an L∞ problem — fine intraday, wrong across closes. The Strategist objected to reflexive Friday-flattening for trend children (weekend continuation is part of the trend edge); the board agreed, which is why the resolution is *pricing*, not prohibition: gap-stressed risk (k× per asset class) counted against budgets for positions held across closes, Friday-reduce default-on only for exchange-gapped assets, and both risk figures shown side-by-side in the GUI. Sizing itself stays stop-based; the *budgets* absorb the tail.

### F-012 — "Earns spread" and "limits don't slip" (HIGH)

The Day Trader vetoed the phrase "earns spread" (01§4 M1) on mechanics: on an OTC/MT5 book you are not a maker, there is no rebate, and a buy limit at the lower band fills when the *ask* touches it — you avoid paying the spread; you earn nothing. The Strategist deepened it into the adverse-selection point that actually matters for edge accounting: passive fills occur conditionally on price trading through your level, so the fill population is negatively selected, and the backtest cost model's "limits don't slip" (05§B2) is the same optimism wearing a different hat — touch-fills at zero cost systematically overstate mean-reversion edges, which then fail their live cones and masquerade as edge decay (F-013's alarm fires for the wrong reason). Resolved here for wording; Pass 7 owns the fill-simulation spec: limit fills require trade-through by ≥1 tick, plus an adverse-selection cost term seeded at half the spread-avoidance credit (hypothesis) and later estimated from live fill-vs-drift telemetry.

### F-013 — MC cone demotion: sequential testing without alpha control (HIGH)

The Quant audited the doc's "most valuable automation" and found an uncontrolled multiple-testing machine: ~24 child×instrument series, each checked against a 95% cone effectively after every trade. Optional-stopping results (literature-informed) put realized type-I for per-observation peeking at nominal 5% over ~100 trades at ≳30% per series — the system will *routinely* halve risk on healthy children, and the Auditor drew the operational conclusion: an alarm that cries wolf gets muted, and a muted edge-decay alarm is worse than none. The Strategist pushed back against over-damping — real decay must still trip it within a tradable horizon. The compromise: block evaluation (every 20 trades / 4 weeks), sequential-aware bounds (CUSUM/SPRT-family, spec'd in Pass 7) with a per-child alpha budget, 95% = WARN-only, automatic action at 99% sustained across two blocks. Detection latency is the explicit price paid for a false-positive rate the operator can trust.

### F-014 — Restart replay trusts broker history (HIGH)

The Architect connected two claims the docs make independently: (04§A1) restart = load state + replay missed candles, and (05§B1) broker M1 history needs a second-source cross-check because it has gaps — the validation chapter distrusts exactly the data the recovery chapter trusts. Incremental structures make it dangerous rather than merely wrong: a gapped replay into a monotonic deque or Wilder chain produces *plausible* values, no exception, so T1 can break out of a channel that never existed and every downstream consumer (regime, viability, snapshots) inherits the poison — silently breaking non-negotiable principle #3 (zero live/backtest drift). Resolution: a replay validator that checks bar continuity against the trading calendar *before* mutating state; any gap ⇒ rebuild affected keys from Parquet + fresh backfill rather than patching; a post-replay checksum canary recomputes a sampled window from scratch and compares.

### F-015 — SQLite: two processes, one writer slot (HIGH)

The Backend Architect held the docs to their own words: 04§A4 grants the core "single-writer to the event log" and, in the same paragraph, has the interface process *writing* confirmations and commands into the same SQLite file — under WAL, writers serialize globally per database, so the confirmation CAS contends with event-log bursts, and bursts co-occur with urgent confirmations by the nature of markets. Worse, timeout resolution (core) and human resolution (interface) write the same confirmation rows from different processes — the single-writer claim is false in the design as written. The Architect's fix is total ownership: the core is the *only* process that opens the DB for writing; the interface talks to the core over the already-specified API/queue and reads via read-only connections. This collapses F-008 and F-015 into one serialization point, which both seats endorsed as the architectural simplification that makes the race analysis tractable. `busy_timeout`, checkpoint cadence, and GUI read-snapshot policy get numbers in Pass 5.

### F-016 — MT5-on-Linux contradiction (HIGH)

The Infra seat put a stake through the ops chapter's silent assumption: the `MetaTrader5` Python package runs only on Windows and only with a live terminal process, while 05§C specifies Docker + systemd — a Linux toolchain. One of the two chapters is wrong, and finding out during deployment is the expensive way. The Algo-Bot Developer catalogued the terminal realities the docs never mention: forced auto-updates, session re-logins, weekly broker restarts, memory creep — all of which need supervision that neither systemd nor Docker will provide on Windows. Two viable shapes exist, both with prior art in this repo: (a) all-Windows VPS (terminal-adjacent, simplest topology, weakest ops tooling), or (b) Linux core + thin Windows bridge (Titan's `bridge/` FastAPI :8766 or the ZMQ EA pattern), preserving the entire specced ops story at the cost of one more hop and failure domain. The board recommends (b) as default — the architecture in 04§A4 is designed for Linux-grade process management — but this is a deployment-reality decision with cost implications: OPEN-FOR-HUMAN, decision matrix due in Pass 5.

### F-017 — Gross-vs-net ambiguity across the limit stack (HIGH)

The Quant walked the seven limits of 02§A2 asking one question of each — gross or net? — and got no answer from the text for any of them, while 02§A3 explicitly introduces *signed* exposure for correlation groups. The interaction is exploitable by accident: long-risk-on plus short-safe-haven passes every written limit while being a single 8% macro bet (the register's example), and overlapping memberships (gold in `metal` class and `safe_haven` group) mean one instrument is double-counted in one dimension and invisible in another. The Auditor termed it double-counting's evil twin: inconsistent counting, which is worse because it fails in both directions unpredictably. The Strategist argued static groups are still right for v1 (dynamic clustering has its own failure modes); the board agreed but demanded the v1 hole be *documented as accepted* if not closed. Resolution in Pass 3: per-limit gross/net declaration, exclusive class membership + explicit group memberships in validated config, a macro-factor cap or an explicit accepted-risk note, and the two register examples as unit tests.

## 4. Cross-cutting themes

**T1 — Claims stated as checkboxes where designs are required.** The two worst offenders are one-liners: "netting handled in the adapter" (F-002) and "bookkeeping preserved per child tranche" hide unsolved problems behind completed-sounding prose. Related: "NTP time sync" (F-033), "minimum-sample thresholds" (F-029), "atomic compare-and-set" (F-008/F-015). Pass rule going forward: any mechanism claim must name its data structure, its owner process, and its failure behavior, or it is a TODO.

**T2 — The asynchronous boundary is systematically under-modeled.** Five findings (F-001, F-008, F-009, F-010, F-015) are the same shape: two actors, one shared fact, no serialization point. The docs model the happy sequence and omit the interleaving. The structural fix adopted across resolutions is one serialized transition owner in the core for all signal/confirmation state — a single decision that dissolves four races at once. Pass 3 must specify the state machine with *every* edge (including fill-during-X edges), and Pass 5 must place the serialization point.

**T3 — Risk-to-stop is treated as the only risk.** F-005, F-011, F-017, F-022, F-034 all reduce to: the ledger measures one projection of risk (distance-to-stop × size, at approved values) and ignores margin, notional, gaps, slippage drift, and counting semantics. The Pass-3 exposure ledger needs three columns per position — risk-at-stop, gap-stressed risk, margin/notional — and every limit annotated gross/net.

**T4 — The cost model is the edge model.** F-003, F-012, F-020, F-021, F-029, F-030 share a root: for retail-sized edges, cost mis-modeling *is* edge mis-estimation — units, adverse selection, session-dependent spreads, double-fill costs, and circular learning feedback each independently overstate viability. The project's charter names cost blindness as a primary killer; this audit finds the current cost math would not prevent it. Pass 7 owns a unified cost-model spec with all terms in ticks, conservative priors as floors, and fill simulation rules per mechanism.

**T5 — Time is an unowned dependency.** Sessions (F-006), day boundaries (F-006), staleness (F-025), clock drift (F-033), expiry/timeout ordering (F-008): four seats independently found time-handling gaps. The system needs a single owned time service — IANA-zone session calendars, broker-offset measurement, monotonic core clock, NTP health — specified once (Pass 4/5) and consumed everywhere.

**T6 — Recovery is rehearsed only on its happy path.** kill-9 replay (05§C) is the easy case; corruption (F-004), gapped history (F-014), unattributable positions (F-032), and spec changes during downtime (F-007) are the cases that destroy accounts. The CI drill suite must include: truncated log, bit-flipped log, gapped broker history, unknown ticket, and spec-diff-while-down.

**T7 — Honesty instrumentation needs the same rigor as the claims it polices.** The three mechanisms built to enforce intellectual honesty — viability gate (F-003), MC demotion cone (F-013), demo gate (F-030) — each had a defect that would make it either inert or noisy. An inert honesty gate is worse than none: it certifies. The Auditor's standing requirement for Pass 7: every gate ships with a *negative control* (a known-bad synthetic child that must fail it) and a *positive control* (a known-marginal child near threshold), run in CI.
